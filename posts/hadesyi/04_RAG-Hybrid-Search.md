# RAG Hybrid Search 실전 가이드 — Dense·BM25·RRF로 검색 정확도 높이기

검색 로그를 열어보면 이런 장면이 반복됩니다. 사용자가 `ERR-4013 승인 거절 코드`를 검색했는데, 벡터 검색은 "결제 실패의 일반적인 원인"이라는 의미상 비슷한 문서를 올려놓고 정작 그 코드가 적힌 표는 Top-10 밖으로 밀어냈습니다. 반대로 키워드 검색만 쓰던 시절에는 "환불이 안 돼요"라는 질문이 "결제 취소 처리 기준" 문서를 전혀 찾지 못했습니다. 앞선 글에서 질문 쪽 불일치를 Query Transformation으로 줄이는 방법을 다뤘는데, 오늘은 검색기 자체를 두 개로 이중화하는 단계입니다. Dense와 BM25는 서로 다른 것을 보고, 서로 다른 방식으로 실패하기 때문입니다.

## 핵심 요약

- Dense 검색과 BM25는 **실패 모드가 서로 다릅니다**. Dense는 코드·모델명·고유명사 같은 정확 매칭에서, BM25는 동의어·구어체 같은 어휘 불일치에서 무너집니다.
- Hybrid Search는 두 검색기를 **병렬로 실행한 뒤 결과를 병합**하는 구성이며, 한쪽의 실패를 다른 쪽이 메우는 상호 보험입니다. 실무 기본값으로 삼을 만합니다.
- 점수를 직접 더하는 병합은 **두 점수의 스케일과 분포가 달라** 위험합니다. 순위만 사용하는 **RRF(Reciprocal Rank Fusion)** 가 가장 안전한 출발점입니다.
- 가중치(α) 튜닝은 골든 셋 없이 하면 의미가 없습니다. **Dense·BM25·Hybrid 세 구성의 Hit@k를 같은 골든 셋으로 비교**한 뒤에 조정하십시오.
- Hybrid로 후보 품질을 올린 다음 병목은 Top-k 정렬입니다. 그 단계는 **Cross-Encoder 리랭커**의 몫입니다.

## 1. 두 검색기는 서로 다른 것을 본다 — 실패 모드부터 구분

Hybrid를 왜 쓰는지는 두 검색기의 실패 사례를 나란히 놓으면 명확해집니다.

| 질문 유형 | 예 | BM25 | Dense |
|---|---|---|---|
| 정확 식별자 | `ERR-4013`, `gpt-oss-120b`, 품번 | 강함 | 약함 |
| 동의어·구어체 | 연차 vs 연차유급휴가 | 약함 | 강함 |
| 신조어·사내 약어 | 임베딩 모델 학습 이후 등장한 용어 | 강함 | 약함 |
| 서술형 개념 질문 | "청크 크기를 어떻게 정하나" | 중간 | 강함 |
| 오탈자 포함 질문 | 쿠버네티스 → 쿠버네터스 | 약함 | 중간 |

BM25는 **질문에 있는 단어가 문서에 그대로 있는가**를 봅니다. 그래서 어휘가 조금만 어긋나도 놓치지만, 일치하기만 하면 확실하게 잡습니다. Dense는 **의미 공간에서의 근접성**을 봅니다. 표현이 달라도 잡아내지만, 임베딩 모델이 학습하지 못한 식별자·신조어에서는 근거 없는 이웃을 올립니다.

> 중요한 것은 "어느 쪽이 더 좋은가"가 아니라 "우리 질문 로그에는 어떤 실패가 많은가"입니다. 두 검색기를 각각 돌려 실패 사례를 유형별로 세어보면, Hybrid가 필요한지 그리고 어느 쪽에 무게를 둘지가 데이터로 나옵니다.

## 2. BM25 쪽 상식 — 점수를 결정하는 세 가지 축

BM25 점수는 세 가지 축의 곱으로 이해하면 충분합니다.

- **IDF** — 희귀한 단어일수록 크게 반영합니다. `승인`보다 `ERR-4013`이 점수를 지배합니다.
- **TF 포화** — 같은 단어가 반복될수록 점수가 오르지만 `k1` 파라미터가 만드는 상한으로 수렴합니다. 한 단어를 100번 쓴 문서가 100배 점수를 받지 않습니다.
- **문서 길이 보정** — 긴 문서는 단어가 우연히 포함될 확률이 높으므로 `b` 파라미터만큼 점수를 깎습니다.

Elasticsearch·OpenSearch·Lucene 계열의 기본값은 `k1=1.2`, `b=0.75`입니다. 이 값을 먼저 만지는 것은 권하지 않습니다. 실무에서 BM25 품질을 좌우하는 것은 파라미터보다 **토크나이저**입니다.

한국어는 이 지점이 특히 중요합니다. 공백 기준 토크나이저로 BM25를 돌리면 `결제가`·`결제를`·`결제는`이 전부 다른 토큰이 되어 매칭이 무너집니다.

```text
"승인 거절 코드를 확인했다"
  공백 토크나이저 → [승인, 거절, 코드를, 확인했다]   ← "코드"로 검색하면 못 찾음
  형태소 분석기   → [승인, 거절, 코드, 확인]          ← 조사·어미 분리
```

- Elasticsearch·OpenSearch에서는 한국어 형태소 분석기 **Nori**를 쓰십시오.
- 애플리케이션 레벨에서 직접 인덱스를 만든다면 **Kiwi** 같은 형태소 분석기로 토큰화한 뒤 BM25 라이브러리에 넣는 구성이 일반적입니다.
- 제품 코드·에러 코드가 중요한 도메인이라면 형태소 분석과 별개로 **원문 그대로의 토큰을 보존**하는 필드를 하나 더 두십시오. 분석기가 `ERR-4013`을 `err`·`4013`으로 쪼개는 사고가 실제로 자주 납니다.

## 3. Dense 쪽 상식 — 잘하는 것과 못하는 것의 경계

Dense 검색은 질문과 문서를 같은 임베딩 공간에 놓고 가까운 것을 찾습니다. 별도 학습 없이 표현 차이를 흡수한다는 것이 최대 강점이고, DPR 계열 연구 이후 사실상 RAG의 기본 검색기가 됐습니다.

경계도 명확합니다.

- **어휘 밖(OOV) 식별자** — 임베딩 모델이 본 적 없는 코드·품번·사내 용어는 의미 공간에서 위치가 불안정합니다.
- **부정·조건의 소실** — "환불이 안 되는 경우"와 "환불이 되는 경우"의 임베딩이 지나치게 가깝습니다.
- **도메인 이동** — 일반 텍스트로 학습한 모델을 법률·의료·사내 문서에 그대로 쓰면 근접성 판단이 흐려집니다. BEIR 벤치마크가 보여준 것이 바로 이 지점입니다. 학습 도메인 밖에서는 튜닝 없는 BM25가 Dense를 이기는 데이터셋이 여럿 있습니다.

청크 품질이 Dense 성능의 전제라는 점은 앞선 청킹 글에서 정리했으므로 여기서는 한 줄만 남깁니다. **임베딩은 청크 단위로 계산되므로, 경계가 무너진 청크는 어떤 검색기로도 구제할 수 없습니다.**

운영 관점의 차이도 하나 짚어둘 가치가 있습니다. Dense 인덱스는 임베딩 모델에 종속됩니다. 모델을 교체하면 전체 문서를 다시 임베딩해야 하고, 문서가 수십만 건이면 이것은 며칠짜리 마이그레이션 작업입니다. 반면 BM25 인덱스는 모델이라는 개념 자체가 없어 토크나이저를 바꾸지 않는 한 그대로 유지됩니다. Hybrid 구성을 갖춰두면 임베딩 모델 마이그레이션 기간 동안 BM25가 품질 하한을 받쳐주는 안전망 역할까지 겸합니다.

## 4. 병합 방법 1 — 점수 결합, 단순하지만 함정이 많다

두 검색기의 점수를 정규화해 가중합하는 방식입니다.

```text
final_score = α · normalize(dense_score) + (1 - α) · normalize(bm25_score)
```

Weaviate의 `alpha` 파라미터가 이 계열이고, min-max 정규화(relativeScoreFusion)를 기본 병합으로 씁니다. 점수 정보를 버리지 않으므로 이론상 상한이 높고, α로 무게를 연속적으로 조절할 수 있습니다.

함정은 정규화 자체에 있습니다.

- **스케일이 다릅니다.** 코사인 유사도는 대략 0~1 사이에 몰리고, BM25는 상한이 없습니다. 정규화 없이 더하면 BM25가 결과를 지배합니다.
- **분포가 다릅니다.** min-max는 그 쿼리의 최고점·최저점에 상대적입니다. 후보가 전부 나쁜 쿼리에서도 1등은 1.0을 받으므로, 절대 품질 정보가 사라집니다.
- **이상치에 약합니다.** BM25 1등이 압도적인 쿼리에서는 min-max가 2등 이하를 전부 0 근처로 눌러버립니다.

> α를 "느낌으로" 0.5에 두고 시작하는 것 자체는 괜찮습니다. 문제는 골든 셋 없이 α를 움직이는 것입니다. 어떤 값이 좋아졌는지 판정할 기준이 없으면 α 튜닝은 소음에 적합(fitting)하는 작업이 됩니다.

## 5. 병합 방법 2 — RRF, 순위만 쓰는 가장 안전한 병합

RRF는 점수를 버리고 **순위만** 씁니다. 각 검색기 결과에서 문서가 rank위에 있으면 `1/(k + rank)`를 얻고, 이를 검색기별로 합산합니다.

```python
from collections import defaultdict

def rrf_fuse(result_lists: list[list[str]], k: int = 60, top_n: int = 20):
    scores = defaultdict(float)
    for results in result_lists:
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)[:top_n]

fused = rrf_fuse([dense_ids, bm25_ids])  # 두 검색기 결과를 그대로 넣는다
```

Query Transformation 글에서 여러 질의의 결과를 병합할 때 쓴 함수와 같은 것입니다. 병합 대상이 "여러 질의"에서 "여러 검색기"로 바뀌었을 뿐입니다.

RRF가 안전한 이유는 명확합니다.

- **스케일 문제가 원천적으로 없습니다.** 순위는 어떤 검색기에서 왔든 같은 단위입니다.
- **파라미터가 사실상 k 하나입니다.** 원 논문이 제안한 `k=60`이 그대로 사실상의 표준 기본값이 됐고, 이 값은 상위권 순위 차이를 완만하게 눌러 한 검색기의 독주를 막습니다.
- **양쪽에 모두 등장하는 문서가 자연스럽게 올라옵니다.** Dense 3위 + BM25 5위인 문서가 한쪽 1위 단독 문서를 이길 수 있습니다. 두 관점이 합의한 문서가 정답일 확률이 높다는 직관과 일치합니다.

한계도 있습니다. 점수 격차 정보를 버리므로, 한 검색기가 압도적 확신을 가진 경우에도 순위 하나로 취급됩니다. 이 손실은 다음 단계인 리랭커가 원문을 다시 읽으면서 보상하는 구조로 설계하는 것이 일반적입니다.

## 6. 실전 구현 — 병렬 실행과 후보 수 설계

Hybrid의 지연시간은 설계만 제대로 하면 단일 검색과 거의 같습니다. 두 검색은 독립적이므로 반드시 병렬로 실행합니다.

```python
import asyncio

async def hybrid_search(query: str, dense, bm25,
                        k_each: int = 50, top_n: int = 20) -> list[str]:
    d_task = asyncio.create_task(dense.search(query, k=k_each))
    b_task = asyncio.create_task(bm25.search(query, k=k_each))
    d_res, b_res = await asyncio.gather(d_task, b_task)
    return rrf_fuse(
        [[d.id for d in d_res], [d.id for d in b_res]],
        top_n=top_n,
    )
```

후보 수는 세 단계로 줄여가는 구성을 기본으로 권합니다.

```text
질문
 ├─ Dense  검색  Top-50 ┐
 │                      ├─ RRF 병합 → Top-20 → Cross-Encoder 리랭커 → Top-5 → LLM
 └─ BM25   검색  Top-50 ┘
```

- **각 검색기에서 넉넉히(예: 50) 뽑습니다.** RRF는 순위 기반이라, 후보 풀이 좁으면 한쪽에만 있는 정답이 병합 전에 잘려나갑니다.
- **두 검색기의 후보 수는 같게 맞춥니다.** 한쪽만 10, 다른 쪽 100이면 `1/(k+rank)` 합산에서 후보가 많은 쪽이 구조적으로 유리해집니다.
- **병합 후 리랭커에 넘기는 수(예: 20)는 리랭커 지연시간 예산으로 결정합니다.** Cross-Encoder는 문서당 추론이 돌기 때문입니다.

## 7. 엔진별 네이티브 지원 — 직접 구현이 필요한 경우와 아닌 경우

주요 엔진은 이미 Hybrid를 네이티브로 지원합니다. 쓰던 엔진에 있으면 그것을 먼저 검토하십시오. 인덱스 두 벌을 앱에서 관리하는 부담이 사라집니다.

| 엔진 | 하이브리드 방식 | 비고 |
|---|---|---|
| Elasticsearch | `retriever` 기반 RRF | RRF는 유료 라이선스 등급 기능이므로 배포 전 라이선스를 확인 |
| OpenSearch | 검색 파이프라인의 정규화·결합 프로세서 | 점수 정규화 방식(min-max 등)을 직접 선택 |
| Qdrant | Query API의 `prefetch` + RRF fusion (1.10+) | 희소 벡터용 IDF 지원 포함 |
| Weaviate | `hybrid` 쿼리의 `alpha` + fusion 선택 | relativeScoreFusion·rankedFusion 중 선택 |
| Milvus | `hybrid_search` + `RRFRanker`/`WeightedRanker` (2.4+) | 다중 벡터 필드 동시 검색 |

엔진이 지원하지 않거나, 검색기 두 개가 서로 다른 시스템에 있다면(예: 벡터 DB + 별도 BM25 라이브러리) 6번의 앱 레벨 RRF 구성을 쓰면 됩니다. RRF는 스무 줄짜리 함수라서 직접 구현이 부담스러운 알고리즘이 아닙니다.

주의할 것은 기능 유무보다 **필터와의 결합 방식**입니다. 메타데이터 필터를 건 상태의 하이브리드 검색은 엔진마다 프리필터·포스트필터 동작이 다르고, 포스트필터로 동작하면 후보가 필터로 깎여 Top-k가 모자라는 사고가 납니다. 필터를 쓰는 서비스라면 반드시 필터를 건 상태로 후보 수를 검증하십시오.

## 8. 평가 — 세 구성을 같은 골든 셋으로 나란히 잰다

Hybrid를 켜는 것은 시작이고, **켜서 좋아졌는지**를 재는 것이 본론입니다. Query Transformation 글의 진단 코드를 확장해 세 구성을 나란히 놓습니다.

```python
def compare_retrievers(golden_set, dense, bm25):
    stats = {"dense": [], "bm25": [], "hybrid": [], "overlap": []}
    for q, gold_ids in golden_set:
        d = [x.id for x in dense.search(q, k=50)]
        b = [x.id for x in bm25.search(q, k=50)]
        h = rrf_fuse([d, b], top_n=50)
        for name, ids in [("dense", d), ("bm25", b), ("hybrid", h)]:
            stats[name].append({
                "hit@5":  float(any(g in ids[:5] for g in gold_ids)),
                "hit@20": float(any(g in ids[:20] for g in gold_ids)),
            })
        stats["overlap"].append(len(set(d[:20]) & set(b[:20])) / 20)
    return stats
```

읽는 법이 중요합니다.

- **overlap(겹침)이 매우 낮다** — 두 검색기가 서로 다른 것을 보고 있다는 뜻이고, Hybrid의 기대 효과가 큽니다. 앞선 글에서 어휘 불일치의 신호로 소개한 바로 그 지표입니다.
- **hybrid가 dense 단독보다 낮다** — 대부분 BM25 쪽 토크나이저 문제거나 후보 수 불일치입니다. Hybrid 자체를 끄기 전에 2번·6번 항목을 먼저 점검하십시오.
- **hit@20은 높은데 hit@5가 낮다** — 후보에는 정답이 들어오는데 정렬이 나쁜 상태입니다. 여기서 필요한 것은 병합 조정이 아니라 리랭커입니다.

골든 셋은 완벽할 필요가 없습니다. 실제 질문 로그에서 뽑은 30~50문항이면 구성 간 우열을 가리기에 충분하고, 없는 것보다 압도적으로 낫습니다.

## 9. 운영 — 인덱스 두 벌을 가진 시스템의 비용

Hybrid는 검색 품질을 사는 대신 운영 복잡도를 지불합니다. 청구서는 세 장입니다.

- **동기화** — 문서를 수정하면 벡터 인덱스와 BM25 인덱스가 **같은 트랜잭션 단위로** 갱신되어야 합니다. 한쪽만 갱신되면 같은 질문에 두 검색기가 서로 다른 버전의 문서를 올리는, 재현도 어려운 장애가 됩니다. 색인 파이프라인의 마지막에 두 인덱스의 문서 수·갱신 시각을 대조하는 점검을 넣으십시오.
- **지연시간** — 병렬 실행이면 max(Dense, BM25)로 수렴합니다. 보통 BM25가 더 빠르므로 체감 추가 지연은 거의 없지만, 리랭커까지 붙인 전체 파이프라인의 TTFT 예산은 별도로 관리해야 합니다.
- **롤아웃** — 한 번에 전 트래픽을 바꾸지 말고, 골든 셋 오프라인 평가 → 일부 트래픽 A/B → 전체 적용 순서를 지키십시오. 검색 구성 변경은 답변 품질에 직결되는데, 원인 추적은 검색 로그 없이는 불가능합니다. 질의·검색기별 Top-k·병합 결과·최종 인용을 로그로 남기는 원칙은 여기서도 같습니다.

비용 구조는 비대칭적입니다. BM25 인덱스는 CPU와 디스크 위주라 추가 비용이 미미한 반면, Dense 쪽은 색인 시점의 임베딩 호출 비용과 ANN 인덱스가 차지하는 메모리가 본체입니다. 즉 이미 Dense 검색을 운영 중이라면 BM25를 얹는 한계 비용은 낮습니다. Hybrid 도입을 망설이게 하는 것은 대부분 비용이 아니라 인덱스 동기화라는 운영 부담이고, 그래서 위의 동기화 점검이 이 구성의 실질적인 진입 조건입니다.

## 10. 흔한 실수

- **점수를 정규화 없이 그대로 더한다** — 상한 없는 BM25 점수가 코사인 유사도를 삼켜 사실상 BM25 단독 검색이 됩니다.
- **한국어 인덱스에 공백 토크나이저 BM25를 쓴다** — 조사·어미 때문에 매칭이 무너져 "BM25는 효과 없다"는 잘못된 결론으로 이어집니다. Nori·Kiwi 같은 형태소 분석기가 전제입니다.
- **골든 셋 없이 α를 튜닝한다** — 판정 기준이 없는 조정은 소음에 맞추는 작업입니다. 측정 체계가 먼저입니다.
- **두 검색기의 후보 수를 다르게 둔다** — RRF 합산에서 후보가 많은 쪽이 구조적으로 유리해져 병합이 편향됩니다.
- **후보 풀을 좁게 잡는다** — 각 검색기 Top-10만 병합하면 한쪽 11위의 정답이 영영 사라집니다. 병합 전 후보는 넉넉히 잡으십시오.
- **Dense 후보만 리랭커에 태운다** — 파이프라인을 개조하다 BM25 결과가 리랭커 입력에서 빠지는 실수가 의외로 잦습니다. 리랭커 입력은 병합 결과여야 합니다.
- **RRF의 k를 반환 개수로 오해한다** — k=60은 순위 완충 상수이지 Top-k가 아닙니다. 반환 개수는 별도 파라미터입니다.
- **식별자 필드를 형태소 분석기에 통과시킨다** — `ERR-4013`이 쪼개져 정확 매칭이라는 BM25의 존재 이유가 사라집니다. 코드류는 원문 보존 필드로 분리하십시오.

## 실전 체크리스트

- 질문 로그에서 정확 매칭 실패와 어휘 불일치 실패 사례를 각각 수집해 Hybrid의 필요성을 데이터로 확인했다.
- 한국어 텍스트에 형태소 분석기(Nori·Kiwi 등) 기반 토크나이저를 적용했다.
- 에러 코드·품번 같은 식별자를 원문 보존 필드로 분리해 인덱싱했다.
- 두 검색기를 병렬로 실행하도록 구현해 추가 지연시간을 max() 수준으로 억제했다.
- 병합 전 각 검색기의 후보 수를 같게, 그리고 넉넉하게(예: 50) 맞췄다.
- 첫 병합 방식으로 RRF(k=60)를 적용하고, 점수 가중 방식은 골든 셋 확보 후 검토 대상으로 미뤘다.
- 사용 중인 엔진의 네이티브 하이브리드 지원 여부와 라이선스 조건을 확인했다.
- 메타데이터 필터를 건 상태에서 후보 수가 모자라지 않는지 검증했다.
- 골든 셋으로 Dense·BM25·Hybrid 세 구성의 Hit@5·Hit@20을 나란히 측정했다.
- 두 검색기 Top-20의 겹침 비율을 측정해 기대 효과를 추정했다.
- 문서 갱신 시 두 인덱스가 함께 갱신되는지 색인 파이프라인에 점검 단계를 넣었다.
- 질의·검색기별 Top-k·병합 결과·최종 인용 여부를 로그로 남겼다.

## 마치며

Hybrid Search는 더 똑똑한 검색기를 만드는 기술이 아니라, 서로 다르게 실패하는 두 검색기로 **실패의 교집합을 줄이는 보험 설계**입니다. 보험이 그렇듯 화려한 개선보다 최악의 상황을 막는 데 가치가 있고, 보험료는 인덱스 두 벌의 운영 비용으로 지불합니다. 그래서 순서가 중요합니다. 토크나이저와 측정 체계라는 기초 없이 병합 파라미터부터 만지면, 보험료만 내고 보장은 받지 못하는 구성이 됩니다.

## FAQ

**Q1. RRF와 점수 가중(α) 방식 중 무엇으로 시작해야 하나요?**

RRF입니다. 정규화 설계 없이도 안전하게 동작하고 파라미터가 사실상 없기 때문입니다. 골든 셋이 갖춰지고 도메인 특성상 한쪽 검색기에 명확히 무게를 줘야 한다는 근거가 생겼을 때 α 방식을 A/B로 검토하십시오.

**Q2. 임베딩 모델이 충분히 좋으면 BM25 없이 Dense만으로 되지 않나요?**

질문 로그에 따라 다릅니다. 서술형 질문 위주라면 Dense 단독도 가능합니다. 하지만 에러 코드·제품명·사내 약어가 섞이는 순간 Dense의 실패 모드가 드러나고, 이는 모델 교체로 해결되지 않는 구조적 한계입니다. BEIR 계열 벤치마크에서 BM25가 여전히 강한 베이스라인인 이유이기도 합니다.

**Q3. 이미 벡터 DB를 쓰고 있는데 BM25 인덱스를 별도로 만들어야 하나요?**

먼저 쓰는 엔진의 네이티브 지원을 확인하십시오. Qdrant·Weaviate·Milvus는 희소/키워드 검색과 병합을 자체 지원하므로 별도 시스템 없이 구성할 수 있습니다. 네이티브 지원이 없을 때만 별도 BM25를 세우고 앱 레벨 RRF로 병합하면 됩니다.

**Q4. Hybrid를 켰는데 지표가 거의 안 움직입니다. 어디를 봐야 하나요?**

세 가지를 순서대로 보십시오. 첫째, 두 검색기 Top-20의 겹침 비율 — 이미 높다면 두 검색기가 같은 것을 보고 있어 병합의 여지가 작습니다. 둘째, BM25 토크나이저 — 한국어에서 형태소 분석 없이 돌고 있다면 BM25가 제 몫을 못 하는 상태입니다. 셋째, Hit@20과 Hit@5의 간극 — 후보에는 정답이 있는데 상위 정렬이 나쁘다면 문제는 병합이 아니라 리랭커 부재입니다.

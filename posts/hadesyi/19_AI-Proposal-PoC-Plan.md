# IT 제안서·PoC 계획서에 AI 도입 과제 쓰는 법 — 요구사항·평가지표·보안 요건 템플릿 (2026)

제안요청서에 "생성형 AI 기반 지능형 검색 서비스 구축" 한 줄이 들어 있고, 제안서 마감은 2주 뒤인 상황. 아키텍처 그림은 금방 그려지는데 막상 본문을 쓰려면 손이 멈춥니다. "정확도 95% 이상"이라고 적어도 되는지, PoC는 무엇을 증명해야 끝나는지, 망분리 환경에서 모델은 어디에 두는지에 답이 없기 때문입니다. AI 과제는 일반 SI 과제와 달리 **결과가 확률적이고 품질이 데이터에 달려 있어서**, 기능 목록만으로는 범위도 검수 기준도 정해지지 않습니다. 앞선 글 「개발자 기술 제안서 목차와 작성 예시」가 제안서의 일반 골격을 다뤘다면, 이 글은 그 안에서 **AI 과제 부분을 어떻게 써야 수주 후에도 지킬 수 있는 문서가 되는지**를 정리합니다.

## 핵심 요약

- AI 과제의 요구사항은 **기능이 아니라 "입력·출력·허용 오차·사람의 개입 지점"** 으로 씁니다. "요약 기능 제공"은 요구사항이 아닙니다.
- 평가지표는 **측정 대상 데이터셋, 측정 방법, 합격 기준**이 한 세트입니다. 셋 중 하나라도 빠진 수치는 검수 단계에서 분쟁이 됩니다.
- PoC 계획서의 핵심은 일정이 아니라 **가설과 종료 조건**입니다. 무엇이 확인되면 본사업으로 가고, 무엇이 확인되면 중단하는지 미리 적으십시오.
- 보안 요건은 **데이터 등급 → 모델 배치 위치 → 통제 항목** 순서로 씁니다. 공공은 C·S·O 등급 분류, 금융은 망분리 예외 절차가 배치 위치를 결정합니다.
- 비용은 구축비가 아니라 **운영 단계의 토큰·GPU·평가 인력 비용**에서 틀어집니다. 요청량 가정과 산식을 제안서에 남기십시오.

## 1. AI 과제가 일반 SI 과제와 다른 점 — 세 가지 불확실성

일반 SI 과제는 화면과 기능이 정해지면 공수가 계산됩니다. AI 과제는 같은 기능 정의에서도 결과 품질이 크게 달라집니다. 제안서가 다뤄야 할 불확실성은 세 가지입니다.

| 불확실성 | 일반 SI | AI 과제 | 제안서에서 다룰 위치 |
| --- | --- | --- | --- |
| 결과 | 결정적(같은 입력, 같은 출력) | 확률적(같은 질문에 다른 답) | 평가지표·검수 기준 |
| 품질 원천 | 구현 코드 | 데이터 상태와 모델 | 데이터 진단·전처리 범위 |
| 변화 속도 | 연 단위 | 모델·가격이 분기 단위로 변경 | 모델 교체 절차·유지보수 범위 |

이 세 가지를 문서에서 다루지 않으면 수주 후에 문제가 됩니다. 발주처는 "제안서에 95%라고 썼다"고 말하고, 수행사는 "그 데이터로는 불가능하다"고 말하는 상황이 대표적입니다. **제안서는 약속 문서**이므로, 약속할 수 없는 것을 약속하지 않는 구조를 먼저 잡아야 합니다.

> AI 과제 제안서의 품질은 기술 설명의 화려함이 아니라, 불확실한 부분을 어디까지 인정하고 어떻게 관리하겠다고 썼는지로 판단됩니다.

## 2. 과제 정의 — "AI 도입"을 업무 단위로 내리기

"AI 기반 업무 혁신"은 과제 정의가 아닙니다. 과제 정의는 **누가, 어떤 업무에서, 무엇을 입력하고, 무엇을 받아, 그 다음에 무엇을 하는지**까지 내려가야 합니다.

```text
[과제 정의 템플릿]
대상 업무   : 민원 답변 초안 작성 (담당자 12명, 월 약 3,000건)
현재 방식   : 담당자가 유사 답변을 수작업 검색 후 작성 (건당 평균 25분)
AI의 역할   : 유사 사례 검색 + 답변 초안 생성
사람의 역할 : 초안 검토·수정·최종 승인 (AI는 발송하지 않음)
입력        : 민원 본문, 첨부 문서(PDF·HWP)
출력        : 근거 문서 링크가 붙은 답변 초안 1건
제외 범위   : 법률 해석이 필요한 민원, 개인정보 열람 청구
기대 효과   : 건당 작성 시간 25분 → 10분 (PoC에서 검증)
```

여기서 가장 중요한 줄은 **사람의 역할과 제외 범위**입니다. AI가 최종 결정을 내리는지, 초안만 만드는지에 따라 검수 기준과 책임 범위, 적용되는 규제가 달라집니다. 기대 효과의 숫자에는 "PoC에서 검증"처럼 **확정치가 아니라는 표시**를 붙이십시오.

과제가 여러 개라면 한 표로 묶어 우선순위를 보여 줍니다. 평가위원은 과제 수가 아니라 **무엇부터 하고 무엇을 미루는지의 판단 근거**를 봅니다.

## 3. 요구사항 작성 — 기능·품질·데이터·운영 네 묶음

AI 과제의 요구사항은 네 묶음으로 나누면 빠지는 것이 줄어듭니다.

| 묶음 | 써야 할 내용 | 나쁜 예 | 좋은 예 |
| --- | --- | --- | --- |
| 기능 | 입력·출력·사람 개입 지점 | 문서 요약 기능 제공 | 20쪽 이하 PDF를 입력받아 500자 이내 요약과 원문 쪽 번호를 반환 |
| 품질 | 지표·데이터셋·합격선 | 높은 정확도 보장 | 평가셋 300문항 기준 근거 일치율 85% 이상 |
| 데이터 | 대상·형식·전처리 책임 | 사내 문서 학습 | 규정집 1,200건(HWP)을 수행사가 변환, 스캔본 OCR 포함 |
| 운영 | 응답 시간·동시 사용자·장애 시 동작 | 안정적 서비스 | 동시 50명 기준 첫 토큰 3초 이내, 모델 장애 시 검색 결과만 반환 |

요구사항 ID 체계는 발주처 양식을 따르되, 각 항목에 **검증 방법**을 함께 적는 편이 좋습니다.

```markdown
| ID | 요구사항 | 검증 방법 | 합격 기준 |
| --- | --- | --- | --- |
| AIR-001 | 답변 초안에 근거 문서 링크를 1개 이상 포함한다 | 평가셋 300건 자동 점검 | 누락률 2% 이하 |
| AIR-002 | 근거 문서에 없는 내용을 답변에 포함하지 않는다 | 평가셋 300건 중 표본 100건 전문가 검토 | 근거 불일치 5건 이하 |
| AIR-003 | 답변 불가 질문에는 불가 사유를 안내한다 | 범위 밖 질문 50건 | 거절 정확도 90% 이상 |
```

AIR-003처럼 **"답하지 않아야 할 때 답하지 않는 것"** 도 요구사항으로 넣으십시오. 운영에서 사고가 나는 지점은 대부분 답을 지어낸 경우이지, 답을 못 한 경우가 아닙니다.

## 4. 평가지표 설계 — 숫자보다 측정 방법이 먼저

"정확도 95%"라는 숫자는 그 자체로는 의미가 없습니다. 지표는 다음 세 가지가 함께 적혀야 성립합니다.

- **데이터셋** — 누가, 몇 건을, 어떤 기준으로 만들었는가. 발주처 실무자가 만든 질문인지 수행사가 만든 질문인지에 따라 난이도가 다릅니다
- **측정 방법** — 자동 채점인지, 사람이 채점하는지, LLM 채점이면 사람 채점과 얼마나 일치하는지
- **합격 기준** — 평균값인지 하한값인지, 미달 시 재평가 절차가 있는지

과제 유형에 따라 쓰는 지표가 다릅니다.

| 과제 유형 | 주 지표 | 보조 지표 |
| --- | --- | --- |
| 문서 검색·질의응답(RAG) | 검색 재현율, 근거 일치율 | 답변 거절 정확도, 응답 시간 |
| 분류·추출 | 정밀도·재현율·F1 | 항목별 오류율, 처리량 |
| 요약·초안 생성 | 사람 평가(5점 척도), 수정률 | 작성 시간 단축률 |
| 에이전트·업무 자동화 | 작업 완료율, 도구 호출 정확도 | 단계 수, 건당 비용 |

제안 단계에서는 발주처 데이터를 볼 수 없는 경우가 많습니다. 이때는 수치를 단정하지 말고 **수치를 정하는 절차**를 약속하십시오.

```text
[평가 기준 확정 절차 — 제안서 기재 예]
1. 착수 후 2주: 발주처 실무자와 평가셋 300문항 공동 구축 (정답·근거 문서 포함)
2. 착수 후 4주: 기준선 측정 (사전 튜닝 없는 상태의 성능)
3. 착수 후 5주: 기준선을 근거로 목표 수치 합의, 과업 지시서에 반영
4. 이후 변경: 평가셋·목표 변경은 양측 서면 합의로만 진행
```

> 목표 수치를 제안서에 적어야만 한다면, 조건을 함께 적으십시오. "발주처가 제공한 평가셋 기준", "전처리가 끝난 문서 범위 내"라는 한정 없이 쓴 숫자는 모든 데이터에 대한 보증으로 읽힙니다.

## 5. PoC 계획서 — 가설·범위·종료 조건

PoC는 작은 본사업이 아닙니다. **본사업 전에 가장 불확실한 것을 확인하는 실험**입니다. 그래서 계획서의 첫 장은 일정이 아니라 가설이어야 합니다.

```yaml
poc:
  name: 민원 답변 초안 생성 PoC
  period: 6주
  hypotheses:
    - id: H1
      statement: 기존 답변 5,000건으로 유사 사례 검색 재현율 80%를 넘길 수 있다
      measure: 평가셋 200문항, recall@5
      pass: ">= 0.80"
    - id: H2
      statement: 담당자가 초안을 수정해 쓰는 시간이 직접 작성보다 짧다
      measure: 담당자 4명, 실제 민원 40건 시간 측정
      pass: 평균 작성 시간 40% 이상 단축
    - id: H3
      statement: 폐쇄망 GPU 2장으로 동시 20명 응답 시간을 맞출 수 있다
      measure: 부하 테스트, 첫 토큰 시간 p95
      pass: "<= 3s"
  out_of_scope:
    - 기간계 시스템 연동
    - 권한별 문서 접근 통제 (본사업 범위)
  exit:
    go: H1, H2 통과
    conditional: H3 미통과 시 장비 증설안과 비용을 재산정해 보고
    stop: H1 미통과 (데이터 정비 선행 필요)
```

이 구조에서 지켜야 할 원칙은 세 가지입니다.

- **가설은 3\~5개** — 그보다 많으면 6\~8주 안에 검증할 수 없습니다
- **종료 조건에 "중단"이 있어야 합니다** — 중단 조건이 없는 PoC는 무조건 성공으로 보고되는 행사가 됩니다
- **제외 범위를 명시합니다** — PoC에서 권한 통제와 연동을 뺐다면, 본사업 공수에 그것이 추가된다는 점도 함께 적으십시오

PoC 결과 보고서의 목차도 계획서에 미리 넣어 두면 좋습니다. 가설별 결과, 실패 사례 분석, 본사업 범위와 공수 재산정이 기본 구성입니다.

## 6. 데이터 요건 — 품질은 데이터에서 결정된다

AI 과제가 지연되는 가장 흔한 원인은 모델이 아니라 데이터입니다. 제안서에는 **데이터를 누가, 어떤 상태로, 언제까지 준비하는지**가 들어가야 합니다.

- **대상과 규모** — 문서 종류, 건수, 형식(HWP·PDF·스캔본), 갱신 주기
- **품질 진단** — 중복·구버전·스캔 품질·표와 도식 비중을 착수 직후 표본으로 진단하고 결과를 보고
- **전처리 책임** — 변환·OCR·개인정보 비식별화를 누가 하는지. 발주처 책임이면 지연 시 일정이 어떻게 조정되는지
- **권한 정보** — 문서별 열람 권한이 원천 시스템에 있는지. 없으면 권한 통제 요구사항은 구현할 수 없습니다
- **평가용 데이터** — 평가셋 구축에 필요한 발주처 실무자의 투입 시간. 이 항목을 빼면 평가가 수행사 주관으로 흐릅니다

> "데이터는 발주처가 제공한다"는 한 줄로는 부족합니다. 제공 형식과 기한, 품질 미달 시의 처리 방식을 적어야 일정 리스크가 문서에 남습니다.

## 7. 보안 요건 — 데이터 등급에서 모델 배치까지

보안 요건은 통제 항목을 나열하기 전에 **모델을 어디에 둘 수 있는지**부터 정해야 합니다. 이 결정은 기술이 아니라 데이터 등급과 발주처에 적용되는 규정이 내립니다.

```text
처리할 데이터가 외부 반출 가능한가?
├─ 가능 (공개 정보) ────────────── 외부 API 사용 검토 가능
├─ 조건부 (내부 업무 정보) ─────── 발주처 보안 기준 확인
│     ├─ 공공: 등급 분류와 보안성 검토 절차 확인
│     └─ 금융: 망분리 예외 절차 확인
└─ 불가 (기밀·민감 정보) ───────── 내부망 모델 서빙 (온프레미스 GPU)
```

- **공공** — 국가 망 보안체계(N2SF)는 업무 정보를 기밀(C)·민감(S)·공개(O)로 분류하고 등급별로 통제를 달리 적용합니다. 등급 분류와 보안성 검토 산출물은 수요기관이 직접 작성해야 하는 부분이므로, 제안서에는 **수행사가 지원하는 범위**를 구분해 적으십시오
- **금융** — 그동안 생성형 AI는 혁신금융서비스 지정으로 망분리 예외를 받아 운영돼 왔고, 2026년 4월에는 단순 모델 변경 시의 절차가 간소화됐습니다. 망분리 제도 자체도 개편이 논의 중이므로, **제안 시점의 기준과 발주처 내부 규정을 확인한 날짜**를 문서에 남기십시오
- **AI 기본법** — 2026년 1월 22일 시행됐습니다. 생성 결과물 표시·고지, 고영향 AI에 해당하는지에 대한 검토 항목을 요구사항에 넣어 두면 감리와 검수에서 설명이 쉬워집니다

배치 위치가 정해지면 통제 항목을 표로 정리합니다.

| 영역 | 통제 항목 |
| --- | --- |
| 입력 | 개인정보·민감정보 탐지와 마스킹, 프롬프트 인젝션 필터 |
| 모델 | 모델·버전 고정, 외부 전송 차단, 학습 재사용 금지 확인 |
| 출력 | 근거 없는 답변 차단, 개인정보 재노출 점검, 생성물 표시 |
| 접근 | 사용자 권한에 따른 검색 범위 제한, 관리자 기능 분리 |
| 기록 | 질의·응답·근거 문서 로그 보관, 보관 기간과 열람 권한 |

> 규제 관련 문장은 단정하지 마십시오. 기준은 계속 바뀌고 기관마다 내부 규정이 다릅니다. 제안서에는 "착수 시 발주처 보안 담당 부서와 적용 기준을 확정한다"는 절차를 넣는 편이 안전합니다.

## 8. 아키텍처와 모델 선택 — 교체 가능성을 문서에 남기기

제안서에 특정 모델 이름을 박아 두면 사업 기간 중에 그 모델이 구버전이 됩니다. 모델 이름은 **제안 시점의 후보**로 적고, 선택 기준과 교체 절차를 본문으로 삼으십시오.

- **선택 기준** — 한국어 성능(발주처 평가셋 기준), 라이선스, 배치 가능 위치, 필요 GPU 메모리, 응답 속도
- **교체 절차** — 새 모델 후보를 같은 평가셋으로 측정하고, 기준 이상일 때만 교체. 이 절차가 있으면 평가셋이 사업 종료 후에도 자산으로 남습니다
- **계층 분리** — 애플리케이션이 모델을 직접 부르지 않고 게이트웨이 계층을 거치게 하면, 모델 교체와 사용량 통제가 한곳에서 이뤄집니다

구성도에는 상자 이름만 적지 말고 **데이터가 어느 경계를 넘는지** 표시하십시오. 평가위원과 보안 담당자가 가장 먼저 확인하는 것이 그 경계입니다.

## 9. 비용·일정·리스크 — 가정을 숨기지 않기

AI 과제의 비용은 구축비보다 운영비에서 예상과 달라집니다. 견적에는 **가정과 산식**을 그대로 남기십시오.

```text
[월 운영 비용 산식 예 — 외부 API 사용 시]
요청 수      : 사용자 200명 × 1일 15건 × 22일 = 66,000건/월
건당 토큰    : 입력 6,000(검색 문맥 포함) + 출력 800
월 토큰      : 입력 3.96억, 출력 0.53억
비용         : (입력 토큰 × 입력 단가) + (출력 토큰 × 출력 단가)
가정         : 캐시 미적용, 재시도 5% 포함, 단가는 제안일 기준 공시가
```

온프레미스라면 같은 방식으로 **동시 사용자와 목표 응답 시간에서 GPU 수량을 역산한 근거**를 적습니다. 여기에 흔히 빠지는 항목이 있습니다. 평가셋을 유지하고 주기적으로 재평가하는 인력, 문서 갱신에 따른 재색인, 모델 교체 검증 비용입니다.

리스크는 일반 항목 대신 AI 과제에 특유한 것을 적고, 각 항목에 대응 방안을 붙이십시오.

| 리스크 | 징후 | 대응 |
| --- | --- | --- |
| 데이터 품질 미달 | 표본 진단에서 스캔본·중복 비중 과다 | 전처리 범위 재산정, 대상 문서 축소 후 단계 확대 |
| 목표 성능 미달 | 기준선이 목표와 크게 벌어짐 | 범위 축소(대상 업무 한정), 사람 검토 단계 유지 |
| 사용자 미정착 | PoC 후 사용률 급감 | 기존 업무 화면에 통합, 수정률 지표로 개선 추적 |
| 모델·가격 변경 | 공급사 정책 변경 공지 | 게이트웨이 계층과 교체 절차로 흡수 |

## 10. 흔한 실수

- **근거 없는 정확도 수치를 적는다** — 데이터셋과 측정 방법 없이 쓴 "95%"는 검수 단계에서 그대로 요구됩니다.
- **PoC와 본사업을 구분하지 않는다** — PoC 범위에서 뺀 권한 통제·연동·운영 체계가 본사업 공수에 반영되지 않아 적자가 납니다.
- **데이터 준비 책임을 비워 둔다** — 전처리와 비식별화가 누구 일인지 없으면, 일정 지연의 책임이 전부 수행사로 옵니다.
- **사람의 검토 단계를 생략한다** — "자동화"를 강조하려고 승인 단계를 빼면, 오답의 책임 범위가 문서상 수행사 시스템에 놓입니다.
- **모델 이름을 확정 사양으로 적는다** — 사업 기간 중 더 나은 모델이 나와도 계약상 교체할 근거가 없어집니다.
- **보안 요건을 일반 체크리스트로 채운다** — 데이터 등급과 모델 배치 위치가 빠진 보안 장은 보안성 검토에서 다시 써야 합니다.
- **운영 비용을 구축비에 묻는다** — 토큰·GPU·재평가 비용이 빠진 견적은 2년 차 유지보수 계약에서 문제가 됩니다.
- **평가를 수행사 혼자 한다** — 발주처 실무자가 참여하지 않은 평가 결과는 검수에서 인정받기 어렵습니다.

## 실전 체크리스트

- 과제마다 대상 업무·입력·출력·사람의 역할·제외 범위를 한 표로 정의했다.
- 요구사항을 기능·품질·데이터·운영 네 묶음으로 나누고 항목마다 검증 방법을 적었다.
- 답변을 거절해야 하는 경우를 요구사항에 포함했다.
- 모든 성능 수치에 데이터셋·측정 방법·합격 기준을 함께 적었다.
- 발주처 데이터를 보지 못한 수치에는 조건이나 확정 절차를 붙였다.
- PoC 계획서 첫 장에 가설과 종료 조건(진행·조건부·중단)을 적었다.
- PoC 제외 범위와 그것이 본사업 공수에 미치는 영향을 명시했다.
- 데이터 대상·형식·전처리 책임·제공 기한을 문서화했다.
- 데이터 등급에 따라 모델 배치 위치를 정하고 그 근거를 남겼다.
- 규제 관련 내용에 확인 일자와 착수 시 확정 절차를 적었다.
- 모델을 후보로 표기하고 선택 기준과 교체 절차를 적었다.
- 운영 비용의 가정과 산식을 견적에 남겼다.

## 마치며

AI 과제 제안서는 기술 소개서가 아니라 **불확실성을 어떻게 나눠 질지에 대한 합의안**입니다. 무엇을 측정하고, 누가 데이터를 준비하고, 어떤 결과가 나오면 멈출지를 문서에 먼저 적어 두면 수주 후의 분쟁 대부분이 사라집니다. 잘 쓴 제안서는 평가 점수보다 사업 종료 시점에 더 큰 차이를 만듭니다.

## FAQ

**Q1. 제안요청서가 "정확도 95% 이상"을 요구하면 어떻게 써야 합니까?**

요구 수치를 그대로 수용한다고 쓰되, 측정 조건을 제안서에서 구체화하십시오. "발주처와 공동 구축한 평가셋 300문항 기준, 전처리가 완료된 문서 범위 내"처럼 데이터셋과 범위를 한정하고, 착수 후 기준선 측정과 목표 합의 절차를 함께 제시합니다. 질의응답 단계에서 지표 정의를 서면으로 질의해 두는 것도 방법입니다.

**Q2. PoC 기간은 어느 정도가 적당합니까?**

가설 3\~5개를 검증하는 데 보통 6\~8주가 필요합니다. 첫 2주는 데이터 확보와 평가셋 구축에 쓰이므로, 4주 이하로 잡으면 측정 없이 시연만 하고 끝나기 쉽습니다. 기간보다 중요한 것은 종료 조건이 미리 합의됐는지입니다.

**Q3. 폐쇄망이라 외부 모델을 쓸 수 없으면 무엇을 적어야 합니까?**

내부망 서빙 구성을 전제로 GPU 수량 산정 근거를 적으십시오. 동시 사용자 수와 목표 응답 시간에서 필요한 처리량을 계산하고, 후보 모델의 메모리 요구량으로 장비를 역산합니다. 모델 반입 절차(파일 반입 승인, 무결성 확인)와 업데이트 주기도 운영 요건에 포함합니다.

**Q4. 평가셋은 누가 만들어야 합니까?**

질문과 정답은 발주처 실무자가, 형식 정리와 채점 도구는 수행사가 맡는 분담이 일반적입니다. 실무자 투입 시간을 제안서에 명시하고(예: 4명이 주 4시간씩 3주), 완성된 평가셋은 발주처 자산으로 귀속시켜 사업 종료 후에도 모델 교체 검증에 쓰도록 하십시오.

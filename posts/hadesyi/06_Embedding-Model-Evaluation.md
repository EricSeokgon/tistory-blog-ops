# 임베딩 모델 선택과 평가 — Cosine·Recall@k·MRR·nDCG 실전 기준

임베딩 모델을 고르는 자리에서 가장 자주 나오는 문장이 있습니다. "리더보드 1위 모델로 가시죠." 그런데 그 모델을 우리 문서에 붙여 골든 셋으로 재보면 3위 모델보다 못한 경우가 드물지 않습니다. 앞선 글들에서 청킹·질의 변환·Hybrid·리랭커를 차례로 다뤘는데, 그 모든 단계가 딛고 서 있는 바닥이 임베딩입니다. 오늘은 그 바닥을 **무엇을 기준으로 고르고, 무엇으로 재는가**를 정리합니다.

## 핵심 요약

- 임베딩 모델 선택은 리더보드 순위가 아니라 **우리 도메인 골든 셋의 지표**로 결정해야 합니다. 벤치마크 1위가 우리 데이터에서 1위라는 보장은 없습니다.
- 유사도는 대부분 **코사인**을 쓰지만, 모델이 정규화 벡터를 내보내는지 먼저 확인하십시오. 정규화되어 있으면 내적(dot)과 코사인이 같은 순위를 냅니다.
- 지표는 **역할이 다릅니다**. Recall@k는 후보에 정답이 들어왔는지, MRR은 첫 정답이 몇 번째인지, nDCG는 여러 정답의 순위 품질까지 봅니다. 하나만 보면 판단이 왜곡됩니다.
- **차원은 공짜가 아닙니다.** 벡터 차원이 커지면 정확도는 조금 오르고 저장·검색 비용은 선형으로 늘어납니다. Matryoshka(MRL) 계열은 잘라 쓰는 선택지를 줍니다.
- 모델 교체는 **전체 재색인**을 뜻합니다. 교체 비용을 먼저 계산하고, 바꿀 만큼의 지표 차이가 있는지 확인한 뒤 결정하십시오.

## 1. 무엇을 고르는 문제인가 — 임베딩 선택의 4가지 축

임베딩 모델은 "성능 좋은 것"으로 고르는 게 아니라, 네 축의 절충으로 고릅니다.

| 축 | 무엇을 보는가 | 실무 판단 |
|---|---|---|
| 검색 품질 | 우리 골든 셋의 Recall@k·nDCG@10 | 리더보드가 아니라 자체 측정값 |
| 언어 대응 | 한국어를 포함한 다국어 학습 여부 | 한국어 문서면 다국어 모델이 전제 |
| 비용·지연 | 차원 수, 색인 시점 임베딩 비용, API vs 자체 서빙 | 문서 수 × 차원이 스토리지를 결정 |
| 운영 제약 | 데이터 외부 반출 가능 여부, GPU 보유 | 반출 불가면 오픈소스 자체 서빙 |

이 중 하나를 극단으로 밀면 나머지가 무너집니다. 최고 품질 모델이 차원 4096이라 벡터 DB 비용이 세 배가 되거나, 가장 싼 모델이 한국어를 못 읽어 Recall이 바닥나는 식입니다. **네 축을 동시에 만족하는 지점**을 골든 셋으로 찾는 것이 이 글의 목표입니다.

> 리더보드는 후보를 3개 정도로 좁히는 데까지만 쓰십시오. 최종 결정은 반드시 우리 문서·우리 질문으로 합니다. 법률·의료·사내 문서처럼 일반 코퍼스와 어휘가 다른 영역일수록 순위가 뒤집힙니다.

## 2. 유사도 — 코사인·내적·L2를 언제 쓰는가

벡터를 비교하는 방법은 셋입니다. 결론부터 말하면 **대부분 코사인**이면 되고, 나머지는 조건이 붙습니다.

- **코사인 유사도** — 두 벡터의 방향만 봅니다. 길이(문서 분량)의 영향을 받지 않아 텍스트 검색의 기본값입니다.
- **내적(dot product)** — 방향과 크기를 함께 봅니다. 벡터가 **정규화되어 있으면 코사인과 순위가 동일**합니다. 정규화 안 된 벡터에 내적을 쓰면 긴 문서가 유리해집니다.
- **L2 거리(유클리드)** — 정규화 벡터에서는 코사인과 단조 관계라 순위가 같습니다. 정규화가 안 되어 있으면 다른 결과를 냅니다.

```python
import numpy as np

def cosine(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# 모델이 정규화 벡터를 주는지 먼저 확인한다
v = model.encode("테스트 문장")
print(np.linalg.norm(v))   # 1.0 근처면 정규화된 벡터
```

실무에서 중요한 것은 **색인과 질의에 같은 방식을 쓰는 것**입니다. 벡터 DB의 거리 함수 설정(예: `COSINE` / `IP` / `L2`)과 모델의 정규화 여부가 어긋나면 검색이 조용히 나빠집니다. 컬렉션을 만들 때 정한 거리 함수는 나중에 바꾸기 어려우므로 처음에 맞추십시오.

이 어긋남이 위험한 이유는 **에러가 나지 않기 때문**입니다. 거리 함수를 잘못 골라도 검색은 정상적으로 결과를 반환합니다. 다만 순위가 미묘하게 나빠질 뿐이라, 빈 결과나 예외처럼 눈에 띄는 신호가 없습니다. 그래서 대개 몇 주 뒤 "답변 품질이 왜 이렇지"라는 막연한 신고로 드러나고, 그때는 원인 후보가 청킹·질의·프롬프트까지 뒤섞여 추적이 어려워집니다. 컬렉션을 만드는 시점에 모델 벡터의 노름을 한 번 찍어보는 30초가 이 상황을 통째로 막아줍니다.

한 가지 더. 비대칭 검색(질문은 짧고 문서는 길다)을 위해 **질의용과 문서용 프리픽스를 따로 요구하는 모델**들이 있습니다. 대표적으로 E5 계열의 `query:` / `passage:` 같은 접두사입니다. 이런 모델에서 프리픽스를 빠뜨리거나 양쪽에 같은 접두사를 붙이면 성능이 눈에 띄게 떨어집니다. 모델 카드에 명시된 사용법을 색인 파이프라인과 질의 경로 **양쪽에** 반영했는지 확인하십시오.

## 3. Recall@k — 후보에 정답이 들어왔는가

Recall@k는 **정답 문서 중 몇 개가 상위 k에 들어왔는지**의 비율입니다. 1단계 검색이 책임지는 지표이고, 리랭커를 붙일 때 N을 정하는 근거가 됩니다.

```python
def recall_at_k(retrieved_ids, gold_ids, k):
    top = set(retrieved_ids[:k])
    return len(top & set(gold_ids)) / len(gold_ids)
```

주의할 점이 하나 있습니다. 앞선 Query Transformation 글에서도 짚었듯, `any()`로 "정답이 하나라도 들어왔는가"를 재면 그것은 Recall이 아니라 **Hit Rate@k**입니다. 정답 문서가 여러 개인 골든 셋에서 두 값은 크게 벌어집니다.

- **Hit Rate@k** — 정답이 하나라도 들어왔으면 1. 답변 가능 여부를 보는 데 적합합니다.
- **Recall@k** — 정답 중 몇 %가 들어왔는지. 정답이 여러 문서에 흩어진 질문에서 중요합니다.

이름을 분리해 로그에 남기지 않으면, 나중에 "Recall이 0.9인데 왜 답을 못 하지?"라는 혼란이 생깁니다.

k를 얼마로 둘지도 목적에 따라 갈립니다. **Recall@50~100**은 리랭커에 넘길 후보 풀이 충분한지 보는 값이고, **Recall@5~10**은 리랭커 없이 바로 LLM에 넣는 구성에서 최종 품질에 직결되는 값입니다. 리랭커를 쓸 계획이라면 큰 k를, 안 쓸 계획이라면 작은 k를 주 지표로 삼으십시오. 둘을 섞어 보면 "Recall은 높은데 답이 부실하다" 같은 어긋난 결론에 도달합니다.

## 4. MRR — 첫 정답이 몇 번째에 오는가

MRR(Mean Reciprocal Rank)은 **첫 번째 정답의 순위 역수**를 평균한 값입니다. 정답이 1위면 1.0, 2위면 0.5, 5위면 0.2입니다.

```python
def mrr(all_retrieved, all_gold):
    total = 0.0
    for retrieved, gold in zip(all_retrieved, all_gold):
        for rank, doc_id in enumerate(retrieved, start=1):
            if doc_id in gold:
                total += 1.0 / rank
                break            # 첫 정답만 본다
    return total / len(all_gold)
```

MRR이 어울리는 상황은 **정답이 사실상 하나인 질문**입니다. "ERR-4013이 무슨 코드인가"처럼 특정 문서 하나만 찾으면 되는 경우, 그 문서가 1위인지 4위인지가 사용자 경험을 가릅니다.

반대로 정답이 여러 문서에 흩어진 질문에서는 MRR이 정보를 많이 버립니다. 첫 정답만 보고 나머지는 무시하기 때문입니다. 그럴 때 필요한 것이 다음 지표입니다.

## 5. nDCG — 여러 정답의 순위 품질까지 본다

nDCG(normalized Discounted Cumulative Gain)는 **정답이 몇 위에 오는지를 로그 가중으로 반영**하고, 이상적인 정렬 대비 몇 %인지로 정규화합니다. 검색 품질 지표 중 가장 정보량이 많아 벤치마크의 기본 지표로 널리 쓰입니다.

```python
import numpy as np

def dcg(relevances):
    return sum(rel / np.log2(i + 2) for i, rel in enumerate(relevances))

def ndcg_at_k(retrieved_ids, gold_map, k):
    # gold_map: {doc_id: 관련도 점수}. 이진이면 정답=1, 그 외=0
    gains = [gold_map.get(d, 0) for d in retrieved_ids[:k]]
    ideal = sorted(gold_map.values(), reverse=True)[:k]
    denom = dcg(ideal)
    return dcg(gains) / denom if denom > 0 else 0.0
```

nDCG의 강점은 두 가지입니다.

- **순위 가중** — 같은 정답이라도 1위와 8위를 다르게 평가합니다. Hit Rate가 놓치는 개선을 잡아냅니다.
- **등급 관련도 지원** — "완전히 맞음 2점 / 부분적으로 맞음 1점"처럼 관련도에 등급을 줄 수 있습니다. 이진 판정보다 현실에 가깝습니다.

다만 등급을 매기려면 골든 셋에 관련도 점수가 있어야 합니다. 처음에는 이진(정답/오답)으로 시작하고, 판정이 애매한 질문이 쌓이면 등급을 도입하는 순서가 현실적입니다.

## 6. 지표를 함께 읽는 법 — 어느 단계가 문제인지 가려낸다

지표 하나만 보면 잘못된 곳을 고치게 됩니다. 세 지표를 함께 놓고 읽으면 병목이 드러납니다.

| Recall@50 | Hit@5 | nDCG@10 | 해석 | 다음 조치 |
|---|---|---|---|---|
| 낮음 | 낮음 | 낮음 | 검색기가 정답을 못 찾음 | 임베딩 모델·청킹·Hybrid 재검토 |
| 높음 | 낮음 | 낮음 | 후보엔 있는데 정렬이 나쁨 | **리랭커 도입** |
| 높음 | 높음 | 중간 | 정답은 상위인데 순서가 최적이 아님 | 리랭커 튜닝·등급 관련도 도입 |
| 높음 | 높음 | 높음 | 검색은 충분함 | 생성 단계·프롬프트로 이동 |

앞선 Reranker 글에서 "Hit@50은 높은데 Hit@5가 낮으면 리랭커"라고 한 판정이 이 표의 두 번째 행입니다. **임베딩 모델을 바꿔야 하는 경우는 첫 번째 행**입니다. Recall@50 자체가 낮다면 후보에 정답이 아예 없다는 뜻이고, 그것은 검색기(=임베딩)의 문제입니다.

다만 첫 번째 행이라고 곧장 모델 교체로 가지 마십시오. Recall이 낮은 원인은 임베딩 말고도 둘이 더 있습니다. **청킹 경계가 무너져** 정답 문장이 두 청크에 걸쳐 잘렸거나, **어휘 불일치**로 질문과 문서가 서로 다른 단어를 쓰고 있는 경우입니다. 앞의 것은 청킹 글이, 뒤의 것은 Hybrid Search와 Query Transformation 글이 다룬 문제입니다. 셋 다 Recall을 떨어뜨리지만 처방이 완전히 다릅니다.

가르는 방법은 간단합니다. **사람이 질문을 문서 용어로 바꿔 써서 검색했을 때 정답이 나오는지** 보십시오. 나온다면 어휘 불일치이므로 Hybrid나 질의 변환이 먼저입니다. 그래도 안 나온다면 청크를 직접 열어 정답 문장이 온전히 한 청크 안에 있는지 확인하십시오. 온전한데도 못 찾는다면, 그때가 임베딩 모델을 의심할 차례입니다.

## 7. 차원과 비용 — 큰 벡터는 공짜가 아니다

임베딩 차원은 품질과 비용을 동시에 결정합니다.

- **저장 비용** — 문서 100만 건 × 1024차원 × float32는 약 4GB입니다. 차원을 3072로 올리면 약 12GB가 됩니다. 벡터 DB 메모리가 선형으로 늘어납니다.
- **검색 지연** — ANN 인덱스의 거리 계산량이 차원에 비례합니다. 차원이 크면 질의당 지연이 늘어납니다.
- **품질 상승폭** — 차원을 두 배로 늘려도 검색 품질은 그만큼 오르지 않습니다. 대개 완만하게 포화됩니다.

**Matryoshka(MRL) 계열 모델**은 이 절충에 선택지를 줍니다. 큰 차원으로 학습하되 앞쪽 차원에 중요한 정보가 몰리도록 훈련해, **뒷부분을 잘라내도 품질 손실이 작습니다.** OpenAI의 text-embedding-3 계열이 `dimensions` 파라미터로 이 방식을 제공하고, Sentence Transformers도 MRL 학습을 지원합니다.

```python
# 차원을 줄여 저장·검색 비용을 낮추는 패턴 (MRL 지원 모델)
full = model.encode(texts)              # 예: 3072차원
small = full[:, :768]                    # 앞 768차원만 사용
small = small / np.linalg.norm(small, axis=1, keepdims=True)   # 재정규화 필수
```

자르고 나면 **반드시 재정규화**하십시오. 잘라낸 벡터는 더 이상 단위 벡터가 아니어서, 정규화를 건너뛰면 코사인 계산이 어긋납니다. 그리고 어디까지 잘라도 되는지는 모델마다 다르므로, 골든 셋으로 차원별 nDCG 곡선을 그려 **품질이 꺾이는 지점 직전**을 고르십시오.

주의할 것은 **MRL로 학습되지 않은 모델을 임의로 자르는 일**입니다. 일반 임베딩 모델은 정보가 전 차원에 고루 퍼져 있어, 뒷부분을 자르면 그만큼 정보가 사라집니다. 모델 카드에 Matryoshka 또는 차원 조절 지원이 명시된 경우에만 자르십시오. 명시가 없다면 차원이 작은 다른 모델을 고르는 편이 안전합니다.

양자화도 함께 검토할 만합니다. float32 대신 **int8이나 binary로 저장**하면 메모리가 각각 1/4, 1/32로 줄어듭니다. 품질 손실이 있지만 차원을 줄이는 것보다 손실 대비 절감이 큰 경우가 많고, 벡터 DB들이 대체로 지원합니다. 차원 축소와 양자화는 배타적이지 않으므로, 스토리지가 병목이라면 둘을 조합해 골든 셋으로 함께 재보십시오.

## 8. 모델 비교 실험 — 후보 3개를 같은 조건에서 재는 법

후보를 좁혔다면 실제로 비교합니다. 핵심은 **임베딩 모델만 바꾸고 나머지를 고정**하는 것입니다.

```python
def compare_embedding_models(models, golden_set, chunks, k=10, n=50):
    results = {}
    for name, model in models.items():
        index = build_index(model.encode(chunks))        # 모델별 인덱스 재구축
        recalls, ndcgs, mrrs = [], [], []
        for q, gold_map in golden_set:
            ids = index.search(model.encode(q), k=n)
            recalls.append(recall_at_k(ids, list(gold_map), n))
            ndcgs.append(ndcg_at_k(ids, gold_map, k))
            mrrs.append(mrr([ids], [set(gold_map)]))
        results[name] = {
            "recall@%d" % n: sum(recalls) / len(recalls),
            "ndcg@%d" % k:   sum(ndcgs) / len(ndcgs),
            "mrr":           sum(mrrs) / len(mrrs),
        }
    return results
```

실험을 신뢰하려면 세 가지를 고정해야 합니다.

- **청킹 동일** — 같은 청크 집합에 각 모델을 태웁니다. 청킹이 다르면 모델 차이인지 청킹 차이인지 구분되지 않습니다.
- **질의 동일** — 질의 변환을 켜지 않은 원본 질문으로 비교합니다. 변환을 켠 채 비교하면 LLM 변동성이 섞입니다.
- **후보 수 동일** — Recall은 n에, nDCG는 k에 민감합니다. 모델마다 값을 다르게 두면 비교가 무의미해집니다.

숫자 차이를 읽을 때도 기준이 필요합니다. 골든 셋이 30~50문항이면 **nDCG 0.01~0.02 차이는 표본 노이즈일 가능성**이 큽니다. 그 정도 차이로 순위를 매기지 말고, 차이가 작다면 품질이 아니라 **비용·차원·운영 제약**으로 결정하십시오. 반대로 5% 이상 벌어진다면 도메인 적합성에서 실제 차이가 났다고 볼 만합니다.

질문 유형별로 쪼개 보는 것도 도움이 됩니다. 전체 평균은 비슷한데 **식별자 질문에서는 A가, 서술형 질문에서는 B가 우세**한 패턴이 자주 나옵니다. 이런 경우라면 모델 선택이 아니라 Hybrid Search로 두 성격을 함께 커버하는 쪽이 정답입니다. 평균 하나만 보면 이 구조를 놓칩니다.

## 9. 운영 — 모델 교체는 전체 재색인이다

임베딩 모델을 바꾸는 순간 **기존 벡터는 전부 무효**가 됩니다. 같은 공간에 있지 않기 때문입니다. 이 사실이 실무에서 갖는 무게는 큽니다.

- **재색인 비용** — 문서 수십만 건이면 임베딩 API 호출 비용과 시간이 며칠 단위로 발생합니다. 교체 전에 반드시 견적을 내십시오.
- **무중단 전환** — 새 인덱스를 별도로 만들어 채운 뒤, 검증이 끝나면 질의 라우팅만 바꾸는 방식(블루-그린)이 안전합니다. 기존 인덱스를 지우는 것은 마지막입니다.
- **버전 기록** — 어떤 인덱스가 어떤 모델·차원·정규화 설정으로 만들어졌는지 메타데이터로 남기십시오. 이것이 없으면 몇 달 뒤 원인 분석이 불가능해집니다.
- **Hybrid의 안전망** — Hybrid Search 글에서 짚었듯, BM25 인덱스는 임베딩 모델과 무관하게 유지됩니다. 재색인 기간 동안 품질 하한을 받쳐줍니다.

> 지표 차이가 크지 않다면 교체하지 않는 것도 결정입니다. nDCG가 0.02 오르자고 며칠짜리 재색인과 리스크를 감수할 이유는 없습니다. **교체 기준선을 미리 정해 두면** 논쟁이 줄어듭니다.

## 10. 흔한 실수

- **리더보드 순위만 보고 고른다** — 벤치마크 코퍼스와 우리 문서의 어휘가 다르면 순위가 뒤집힙니다. 자체 골든 셋으로 최종 판정하십시오.
- **Hit Rate를 Recall이라 부른다** — 정답이 여러 개인 골든 셋에서 두 값은 크게 다릅니다. 이름을 분리해 로그에 남기십시오.
- **지표 하나만 본다** — Recall만 보면 정렬 문제를, nDCG만 보면 후보 누락을 놓칩니다. 세 지표를 함께 읽으십시오.
- **정규화 여부를 확인하지 않는다** — 정규화 안 된 벡터에 내적을 쓰면 긴 문서가 유리해집니다. 벡터 노름을 한 번 찍어보십시오.
- **벡터 DB 거리 함수와 모델 설정이 어긋난다** — 컬렉션의 거리 함수는 나중에 바꾸기 어렵습니다. 처음에 맞추십시오.
- **차원을 자르고 재정규화를 안 한다** — MRL 모델을 잘라 쓸 때 재정규화를 빠뜨리면 코사인 계산이 틀어집니다.
- **모델만 바꿔 비교한다면서 청킹도 같이 바꾼다** — 무엇이 개선의 원인인지 알 수 없게 됩니다. 한 번에 하나만 바꾸십시오.
- **재색인 비용을 계산하지 않고 교체를 결정한다** — 수십만 건 재임베딩은 며칠짜리 작업입니다. 견적 먼저입니다.

## 실전 체크리스트

- 리더보드로 후보를 2~3개로 좁힌 뒤, 최종 결정은 자체 골든 셋으로 했다.
- 한국어 문서라면 다국어 학습 모델인지 확인했다.
- 모델이 정규화 벡터를 내보내는지 벡터 노름으로 확인했다.
- 벡터 DB 컬렉션의 거리 함수를 모델 설정과 일치시켰다.
- Hit Rate@k와 Recall@k를 이름으로 구분해 각각 측정했다.
- Recall@50·Hit@5·nDCG@10을 함께 재서 병목이 검색기인지 정렬인지 판정했다.
- 후보 모델들을 동일한 청크·동일한 질의·동일한 k/n으로 비교했다.
- 차원별 nDCG 곡선을 그려 품질이 꺾이기 직전 차원을 선택했다.
- MRL 모델을 잘라 썼다면 재정규화를 적용했다.
- 문서 수 × 차원으로 스토리지·메모리 증가분을 계산했다.
- 모델 교체 시 재색인 비용과 소요 시간을 미리 견적했다.
- 인덱스 메타데이터에 모델명·차원·정규화 설정·생성 일시를 기록했다.

## 마치며

임베딩 모델 선택은 "가장 좋은 모델 찾기"가 아니라 **우리 문서와 우리 질문에 가장 덜 어긋나는 모델 찾기**입니다. 그래서 답은 리더보드가 아니라 골든 셋에 있고, 판정은 하나의 숫자가 아니라 Recall·MRR·nDCG가 함께 그리는 그림에 있습니다. 그리고 이 선택은 한 번 하면 되돌리는 데 재색인이라는 비용이 붙습니다. 서두르지 말고, 재고 나서 고르십시오.

## FAQ

**Q1. 코사인과 내적 중 무엇을 써야 하나요?**

모델이 정규화 벡터를 내보낸다면 둘은 같은 순위를 냅니다. 이 경우 내적이 계산이 조금 더 싸므로 벡터 DB가 지원하면 내적을 써도 됩니다. 정규화가 보장되지 않으면 코사인을 쓰십시오. 어느 쪽이든 색인과 질의에 같은 기준을 적용하는 것이 핵심입니다.

**Q2. 골든 셋이 몇 개나 있어야 비교가 의미 있나요?**

실제 질문 로그에서 뽑은 30~50문항이면 후보 간 우열을 가리는 데 충분한 경우가 많습니다. 완벽한 골든 셋을 만들려다 시작을 미루는 것보다, 작게라도 만들어 재기 시작하는 편이 낫습니다. 판정이 애매한 질문이 쌓이면 그때 등급 관련도를 도입해 확장하십시오.

**Q3. 차원을 줄이면 검색 품질이 얼마나 떨어지나요?**

모델과 도메인에 따라 다릅니다. MRL로 학습된 모델은 상당 부분 잘라내도 손실이 작게 설계되어 있지만, 그 "상당 부분"이 어디까지인지는 직접 재봐야 합니다. 차원을 여러 단계로 잘라 nDCG를 측정해 곡선을 그리고, 꺾이는 지점 직전을 고르는 것이 안전합니다.

**Q4. 새 모델이 나올 때마다 교체해야 하나요?**

아닙니다. 교체는 전체 재색인을 뜻하므로 비용과 리스크가 있습니다. 미리 **교체 기준선**을 정해 두십시오. 예를 들어 "자체 골든 셋 nDCG@10이 5% 이상 개선되고, 차원·비용이 현재 이하일 때만 교체한다" 같은 규칙이면 매번 논쟁하지 않아도 됩니다.

# vLLM Structured Outputs 완전정리 — JSON Schema·Regex·Grammar로 출력 형식 강제하기

LLM에 "JSON으로만 답해"라고 아무리 강하게 써도 열 번에 한 번은 앞에 설명이 붙거나 마지막 중괄호가 빠집니다. 파서는 그 한 번에 터지고, 재시도 로직이 붙고, 재시도가 또 실패합니다. **프롬프트로는 형식을 보장할 수 없습니다.** 형식은 요청 사항이 아니라 디코딩 단계에서 강제해야 하는 제약이기 때문입니다. vLLM의 Structured Outputs는 바로 그 지점을 건드립니다. 이 글은 다섯 가지 제약 방식, 백엔드 선택, 스키마 함정, 성능 비용을 실전 기준으로 정리합니다.

## 핵심 요약

- 구조화 출력은 프롬프트 기법이 아니라 **로짓 마스킹**입니다. 매 토큰마다 문법상 불가능한 토큰을 후보에서 제거하므로 형식 위반이 **구조적으로 불가능**해집니다.
- 제약은 다섯 가지입니다 — `choice`, `regex`, `json`, `grammar`, `structural_tag`. 필요한 만큼만 좁게 거는 것이 성능과 품질 모두에 유리합니다.
- 파라미터 이름이 **바뀌었습니다.** 예전 `guided_json` 계열은 `structured_outputs` 아래로 통합됐습니다. 예제를 복사할 때 버전을 먼저 확인하십시오.
- 백엔드는 `auto`가 기본입니다. **xgrammar**는 캐싱과 장문 생성에, **guidance**는 첫 토큰 지연과 동적 스키마에 강합니다.
- 가장 위험한 함정은 **조용한 제약 누락**입니다. xgrammar가 못 받는 JSON Schema 키워드(`minItems`, `maxItems`, `uniqueItems` 등)를 넣으면 폴백이 제때 안 걸릴 경우 **제약이 무시된 채 통과**합니다.
- 구조화 출력은 값의 **형식**을 보장할 뿐 **내용의 정확성**은 보장하지 않습니다. 스키마를 통과한 헛소리는 여전히 헛소리입니다.

## 1. 구조화 출력은 프롬프트가 아니라 디코딩 제약이다

LLM은 매 스텝마다 어휘 전체에 대한 로짓을 뽑고 그중 하나를 샘플링합니다. 구조화 출력은 **샘플링 직전에 마스크를 씌웁니다.**

지금까지 생성된 토큰이 `{"name":` 라면, 문법상 다음에 올 수 있는 것은 공백이나 여는 따옴표뿐입니다. 나머지 토큰의 로짓을 `-inf`로 눌러버리면 모델은 유효한 토큰만 고를 수 있습니다.

```
로짓 →  [문법 상태기가 유효 토큰 집합 계산]  →  마스크 적용  →  샘플링
                    ↑
        지금까지 생성된 토큰으로 상태 전이
```

프롬프트 방식과의 차이는 확률의 문제가 아니라 **가능/불가능의 문제**입니다. 프롬프트는 유효한 형식의 확률을 높일 뿐이고, 확률이 아무리 높아도 0이 아닌 꼬리가 남습니다. 하루 10만 건을 처리하면 그 꼬리는 매일 수십 건의 파싱 실패로 나타납니다. 마스킹은 그 꼬리를 **잘라냅니다.**

여기서 중요한 성질이 나옵니다.

- **형식 위반이 불가능합니다.** "가끔 실패한다"가 아니라 "실패할 수 없다"입니다
- **재시도 루프가 사라집니다.** 파싱 실패 재시도는 구조화 출력을 쓰는 순간 설계에서 빠집니다
- **대신 내용은 보장되지 않습니다.** 스키마가 `{"age": int}`면 모델은 반드시 정수를 뱉지만, 그 정수가 맞는 값인지는 별개입니다

> 💡 이 구분이 실무에서 가장 자주 흐려집니다. 구조화 출력을 켠 뒤 "이제 정확해졌다"고 말하는 팀이 있는데, 정확해진 것은 **파싱 성공률**이지 **답의 품질**이 아닙니다. 품질은 여전히 프롬프트와 검색 품질의 문제입니다.

## 2. 다섯 가지 제약 — 좁게 걸수록 좋다

vLLM이 제공하는 제약은 다섯 가지입니다.

| 제약 | 쓰는 상황 | 표현력 |
| --- | --- | --- |
| `choice` | 분류·라우팅. 정해진 라벨 중 하나 | 가장 좁음 |
| `regex` | 날짜·이메일·ID 같은 고정 패턴 | 좁음 |
| `json` | 구조화된 객체 추출 | 넓음 |
| `grammar` | JSON으로 안 되는 DSL·SQL 부분집합 | 가장 넓음 |
| `structural_tag` | 태그 안쪽만 스키마로 강제 | 혼합 |

**가능한 한 좁은 제약을 쓰는 것이 원칙입니다.** 감성 분류에 JSON 스키마를 씌우는 것보다 `choice=["positive","negative"]`가 낫습니다. 문법이 단순할수록 컴파일이 빠르고, 마스크 계산이 가볍고, 모델이 헷갈릴 여지도 줄어듭니다.

`grammar`는 EBNF로 문맥자유문법을 직접 씁니다. JSON으로 표현할 수 없는 형식 — 제한된 SQL 부분집합, 사내 쿼리 DSL, 특정 마크업 — 이 필요할 때만 꺼내십시오. 표현력이 가장 넓은 대신 문법을 직접 관리해야 하고 컴파일도 가장 비쌉니다.

`structural_tag`는 다소 특이한데, **출력 전체가 아니라 특정 태그 안쪽만** 스키마로 묶습니다. 모델이 자연어로 설명하다가 `<tool_call>...</tool_call>` 안에서만 정확한 JSON을 내야 하는 도구 호출 시나리오가 대표적입니다. 출력 전체를 JSON으로 묶으면 모델이 설명할 자리를 잃는데, 이 방식은 자연어와 구조화 영역을 한 응답 안에 공존시킵니다.

## 3. OpenAI 호환 API — 두 가지 경로

vLLM 서버는 OpenAI 클라이언트로 붙습니다. 제약을 거는 경로가 두 개인데 성격이 다릅니다.

**경로 1 — `extra_body`의 `structured_outputs`.** vLLM 고유 확장이고 다섯 제약을 전부 씁니다.

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

# 분류: 라벨 중 하나만
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "이 리뷰의 감성은? 배송이 너무 느려요"}],
    extra_body={"structured_outputs": {"choice": ["positive", "negative"]}},
)

# 패턴: 이메일 형식만
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "회사 이메일 주소를 하나 만들어줘"}],
    extra_body={"structured_outputs": {"regex": r"\w+@\w+\.com\n"}},
)
```

**경로 2 — 표준 `response_format`.** OpenAI API와 호환되므로 클라이언트 코드를 그대로 옮길 수 있습니다.

```python
from pydantic import BaseModel
from enum import Enum

class Severity(str, Enum):
    low = "low"
    high = "high"

class Incident(BaseModel):
    service: str
    severity: Severity
    summary: str

completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "장애 로그를 요약해줘: ..."}],
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "incident", "schema": Incident.model_json_schema()},
    },
)
```

> ⚠️ **파라미터 이름이 바뀌었습니다.** 예전에는 `extra_body={"guided_json": ...}`, `guided_choice`, `guided_regex` 처럼 평평한 이름을 썼습니다. 지금은 `structured_outputs` 딕셔너리 아래로 모였습니다. 인터넷의 예제는 대부분 옛 이름이라 그대로 붙이면 **제약이 무시된 채 조용히 통과**합니다. 알 수 없는 키를 서버가 그냥 버리기 때문입니다. 버전에 맞는 공식 문서를 먼저 확인하십시오.

## 4. 오프라인 추론 — 배치 파이프라인에서

서버를 띄우지 않고 파이썬에서 직접 돌릴 때는 `SamplingParams`에 실어 보냅니다.

```python
from vllm import LLM, SamplingParams
from vllm.sampling_params import StructuredOutputsParams

llm = LLM(model="HuggingFaceTB/SmolLM2-1.7B-Instruct")

so = StructuredOutputsParams(choice=["Positive", "Negative"])
params = SamplingParams(structured_outputs=so)

outputs = llm.generate(
    prompts="Classify this sentiment: vLLM is wonderful!",
    sampling_params=params,
)
```

대량 라벨링이나 데이터셋 생성처럼 **같은 스키마를 수만 건에 반복 적용**하는 작업이 오프라인 경로의 주 무대입니다. 이때 문법 컴파일 결과가 캐시되므로, 스키마 하나로 배치를 통째로 도는 것이 스키마를 건마다 바꾸는 것보다 훨씬 빠릅니다.

## 5. 백엔드 — 언제 바꿔야 하나

vLLM은 제약을 실제로 집행하는 백엔드를 갈아 끼울 수 있습니다. 기본값은 `auto`이고, 요청 내용을 보고 알아서 고릅니다.

```bash
vllm serve <model> --structured-outputs-config.backend auto
```

성격이 갈리는 지점은 이렇습니다.

| 백엔드 | 강점 | 맞는 워크로드 |
| --- | --- | --- |
| xgrammar | 문법 캐싱, 장문 생성 최적화 | 스키마가 고정된 프로덕션 서비스 |
| guidance | 첫 토큰 지연(TTFT) 단축 | 멀티테넌트, 요청마다 스키마가 다른 경우 |
| outlines | 넓은 스키마 호환성 | xgrammar가 못 받는 스키마의 폴백 |

- **xgrammar** — 문법 컴파일 결과를 캐싱합니다. **같은 스키마가 반복**되고 **출력이 긴** 워크로드에 강합니다. 대부분의 서비스가 여기 해당합니다
- **guidance** — 첫 토큰까지의 지연이 짧습니다. **매 요청 스키마가 다른** 멀티테넌트 환경에 유리합니다
- **outlines** — 오래된 기본 백엔드였고, xgrammar가 못 받는 스키마의 폴백 대상으로 자주 등장합니다

> 💡 백엔드를 처음부터 고정하지 마십시오. `auto`로 두고 운영하다가 **TTFT가 튄다면 guidance**, **긴 JSON 생성이 느리다면 xgrammar** 쪽으로 실측하며 옮기는 순서가 안전합니다. 백엔드 교체는 코드 변경 없이 서버 플래그만 바꾸면 됩니다.

참고로 vLLM V0에서는 제약 요청 하나가 배치 전체의 처리량을 떨어뜨렸습니다. V1에서는 백엔드 최적화로 이 오버헤드가 크게 줄었습니다. **버전이 성능 판단을 통째로 바꾸므로**, 오래된 벤치마크 글을 근거로 결정하지 마십시오.

## 6. 스키마 함정 — 조용히 무시되는 제약들

여기가 이 글에서 가장 실용적인 부분입니다.

xgrammar는 JSON Schema 전체를 지원하지 않습니다. 배열 관련 키워드 중 다음은 받지 못합니다.

- `minItems` / `maxItems`
- `uniqueItems`
- `contains` / `minContains` / `maxContains`

문제는 **못 받는다는 사실 자체가 아니라 그다음 동작**입니다. vLLM은 지원되지 않는 스키마를 감지하면 다른 백엔드로 폴백하도록 설계돼 있는데, **감지 함수가 모든 키워드를 다 보지 못하던 시기가 있었습니다.** 그 경우 폴백이 걸리지 않고 xgrammar가 그대로 처리하면서 **해당 제약만 조용히 사라집니다.**

```python
# 위험한 스키마 — 배열 길이 제약이 무시될 수 있다
{
  "type": "object",
  "properties": {
    "tags": {
      "type": "array",
      "items": {"type": "string"},
      "minItems": 3,        # ← 백엔드가 못 받으면 무시될 수 있음
      "maxItems": 5
    }
  }
}
```

에러가 나면 차라리 낫습니다. **조용히 통과하는 쪽이 훨씬 위험합니다.** 태그가 1개만 오거나 20개가 와도 파싱은 성공하므로 다운스트림에서야 문제가 드러납니다.

> ⚠️ **스키마 제약을 애플리케이션에서 한 번 더 검증하십시오.** 구조화 출력은 타입과 구조를 보장하지만 **개수·범위·유일성 제약까지 보장한다고 가정하면 안 됩니다.** Pydantic 모델로 받은 뒤 `model_validate()` 를 다시 태우는 정도의 이중 방어가 적정합니다.

여담으로 공백 처리도 자주 걸립니다. JSON 문법상 요소 사이에 공백이 얼마든 올 수 있어서, 모델이 공백만 계속 뱉으며 토큰을 소모하는 패턴이 나올 수 있습니다. `disable_any_whitespace` 계열 옵션은 이 여지를 막는 장치입니다.

## 7. 성능 — 제약은 공짜가 아니다

비용은 두 군데서 발생합니다.

**컴파일 비용.** 스키마나 정규식을 상태기로 변환하는 작업입니다. 스키마가 크고 중첩이 깊을수록 비쌉니다. **같은 스키마를 재사용하면 캐시가 먹히므로** 실질 비용은 첫 요청에 몰립니다.

**마스킹 비용.** 매 토큰마다 유효 토큰 집합을 계산해 마스크를 만드는 작업입니다. 이건 토큰 수에 비례해 계속 발생합니다.

여기서 실전 지침이 나옵니다.

- **스키마를 요청마다 동적으로 만들지 마십시오.** 필드 순서만 달라져도 다른 스키마로 취급돼 캐시가 빗나갑니다
- **중첩을 얕게 유지하십시오.** 3단 중첩 객체보다 평평한 객체 두 개가 대체로 빠릅니다
- **`choice`로 될 일에 `json`을 쓰지 마십시오.** 문법이 단순할수록 두 비용이 모두 내려갑니다
- **출력 길이를 제한하십시오.** 마스킹 비용은 생성 토큰 수에 비례합니다

측정할 때는 **첫 요청과 이후 요청을 반드시 나눠서** 보십시오. 컴파일 비용이 첫 요청에 몰리므로, 워밍업 없이 잰 p99는 실제 운영 지연을 크게 과장합니다. 반대로 스키마가 요청마다 달라지는 서비스라면 그 첫 요청 비용이 **매번** 발생하므로, 워밍업된 수치로 용량을 잡으면 과소 산정이 됩니다.

> 💡 서비스 기동 직후 주요 스키마로 더미 요청을 한 번씩 태워 캐시를 데워 두십시오. 헬스체크에 이 워밍업을 포함시키면 배포 직후의 지연 스파이크가 사라집니다.

## 8. 추론 모델과 함께 쓰기

reasoning 계열 모델은 생각 과정과 최종 답을 섞어 냅니다. 여기에 스키마를 그대로 걸면 **생각 과정까지 JSON이 되어야 하는** 모순이 생깁니다.

vLLM은 reasoning 파서로 둘을 분리한 뒤 최종 답에만 제약을 겁니다.

```python
completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "..."}],
    response_format={
        "type": "json_schema",
        "json_schema": {"name": "people", "schema": People.model_json_schema()},
    },
)
print("reasoning:", completion.choices[0].message.reasoning)
print("content:  ", completion.choices[0].message.content)
```

모델에 따라 reasoning 내용이 별도 필드로 분리되지 않으면 구조화 출력이 아예 비활성화될 수 있습니다. 그럴 때는 서버 기동 플래그로 명시합니다.

```bash
vllm serve <model> --structured-outputs-config.enable_in_reasoning=True
```

## 9. 운영 — 실패를 설계에 넣는다

구조화 출력을 켰다고 실패가 사라지지는 않습니다. 실패의 **모양이 바뀔** 뿐입니다.

- **컴파일 실패** — 스키마가 백엔드 지원 범위를 벗어나면 요청 자체가 거부될 수 있습니다. 스키마는 배포 전에 한 번 실제로 태워보십시오
- **길이 초과** — 스키마를 다 채우기 전에 `max_tokens`에 걸리면 **잘린 JSON**이 나옵니다. 이건 구조화 출력이 막아주지 못합니다
- **무한 공백** — 문법이 허용하는 공백을 계속 뱉는 패턴. 공백 옵션과 길이 제한을 같이 걸어두십시오
- **의미 없는 유효값** — 필수 필드를 채우기 위해 모델이 빈 문자열이나 `"unknown"`을 넣는 경우. 스키마에 `enum`이나 패턴을 얹어 좁히십시오

운영 지표로는 **파싱 성공률이 아니라 스키마 통과 후 애플리케이션 검증 실패율**을 보십시오. 앞의 것은 구조화 출력을 켜는 순간 100%가 되므로 아무것도 알려주지 않습니다.

함께 볼 지표를 두 개 더 꼽자면 **잘린 응답 비율**(finish_reason이 length인 비율)과 **스키마별 첫 요청 지연**입니다. 전자는 `max_tokens` 설정이 스키마 크기에 못 미친다는 신호이고, 후자가 계속 높다면 캐시가 안 먹고 있다는 뜻입니다.

## 10. 흔한 실수

- **옛 파라미터 이름을 그대로 쓴다** — `guided_json`은 무시될 수 있습니다. 무시돼도 응답은 정상으로 보이므로 발견이 늦습니다
- **프롬프트의 형식 지시를 지운다** — 제약을 걸어도 프롬프트에 "JSON으로 답하라"를 남겨두는 편이 품질이 낫습니다. 모델이 무엇을 생성 중인지 알고 있어야 내용이 맞습니다
- **스키마에 설명을 안 넣는다** — `description` 필드는 프롬프트처럼 작동합니다. 필드 이름만으로 의도가 전달되지 않으면 채워 넣으십시오
- **제약을 최대한 넓게 건다** — "혹시 모르니 optional로" 가 쌓이면 모델이 전부 생략한 최소 JSON을 냅니다. 필요한 것은 `required`로 못 박으십시오
- **구조화 출력으로 환각을 잡으려 한다** — 형식과 사실은 별개입니다. 근거가 필요하면 검색 품질을 손보십시오

## 실전 체크리스트

- 가장 좁은 제약을 골랐다 (`choice` < `regex` < `json` < `grammar`)
- 파라미터 이름을 **설치된 vLLM 버전 문서로** 확인했다
- 스키마를 배포 전에 실제 서버에 태워 컴파일 성공을 확인했다
- `minItems` 같은 배열 제약에 의존하지 않거나, 애플리케이션에서 재검증한다
- 스키마를 요청마다 새로 만들지 않는다 (캐시 적중 유지)
- `max_tokens`가 스키마를 다 채울 만큼 충분하다
- 프롬프트에도 형식 지시를 남겨 두었다
- 애플리케이션 단 검증 실패율을 지표로 보고 있다

## 마치며

구조화 출력은 **LLM 출력을 신뢰할 수 있게 만드는 기술이 아니라, 신뢰할 수 없는 출력을 안전하게 다루는 경계를 만드는 기술**입니다. 파싱이라는 불확실성을 시스템에서 제거해 주는 대신, 내용의 정확성이라는 진짜 어려운 문제는 그대로 남겨 둡니다.

그래서 도입 순서가 중요합니다. 먼저 구조화 출력으로 **형식 실패를 0으로 만들어** 관측 가능한 상태를 만들고, 그다음 남은 실패가 검색 문제인지 프롬프트 문제인지 모델 문제인지 가려내는 것이 순서입니다. 형식 실패가 섞여 있으면 그 진단 자체가 불가능합니다.

## FAQ

**Q1. 함수 호출(tool calling)과 구조화 출력은 다른 기능인가요?**

내부적으로는 같은 메커니즘을 씁니다. 도구 호출도 결국 정해진 스키마의 JSON을 내야 하는 문제이므로 제약 디코딩으로 구현됩니다. `structural_tag`가 태그 안쪽만 스키마로 묶는 것도 이 시나리오를 겨냥한 설계입니다.

**Q2. 작은 모델에서도 쓸 수 있나요?**

형식 준수는 오히려 작은 모델에서 효과가 큽니다. 큰 모델은 프롬프트만으로도 형식을 대체로 지키지만 작은 모델은 자주 어긋나기 때문입니다. 다만 **내용 품질은 모델 크기를 따라가므로**, 형식이 맞는다고 작은 모델로 내려도 된다는 뜻은 아닙니다.

**Q3. 정규식 제약은 얼마나 복잡해도 되나요?**

복잡할수록 상태기가 커지고 컴파일이 비싸집니다. 백트래킹이 필요한 패턴이나 지나치게 중첩된 그룹은 피하십시오. 정규식으로 표현이 힘들어지는 시점이 오면 대개 `json`이나 `grammar`로 옮길 때입니다.

**Q4. 스트리밍과 같이 쓸 수 있나요?**

쓸 수 있습니다. 제약은 토큰 단위로 걸리므로 스트리밍과 충돌하지 않습니다. 다만 클라이언트에서 부분 JSON을 파싱해야 하므로, 스트리밍 중간 상태를 다룰 파서를 따로 준비해야 합니다.

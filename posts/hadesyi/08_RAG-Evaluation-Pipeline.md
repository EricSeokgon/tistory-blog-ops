# RAG 평가 파이프라인 — 골든 셋 구축과 회귀 테스트

앞선 글들에서 하이브리드 검색, 리랭커, 임베딩 모델 선택을 다루면서 매번 같은 말로 끝맺었습니다. **"골든 셋으로 측정하고 도입하십시오."** 그런데 그 골든 셋을 어떻게 만드는지는 한 번도 쓰지 않았습니다. 이 글이 그 빚을 갚습니다. 질문 100개를 어디서 구하고, 정답을 어떻게 붙이고, 그걸 어떻게 CI에 넣어 다음 배포가 검색 품질을 깎아먹는 순간 빨간불이 켜지게 만드는지 — 처음부터 끝까지 정리합니다.

## 핵심 요약

- 평가 파이프라인이 없으면 RAG 튜닝은 **되돌아옵니다.** 지난주에 좋아 보였던 변경이 이번 주 변경으로 상쇄되는데 아무도 모릅니다.
- **검색과 생성을 반드시 분리해 측정하십시오.** 최종 답변만 보면 검색이 못 가져온 건지 LLM이 못 읽은 건지 구분할 수 없습니다.
- 골든 셋은 **50개면 시작할 수 있고, 150~300개면 충분**합니다. 크기보다 **분포**가 중요합니다.
- 질문은 **실제 로그에서** 뽑는 것이 원칙입니다. 합성 질문은 초기 부트스트랩용이지 최종 기준이 아닙니다.
- 검색 지표는 **Recall@k를 1순위**로 보십시오. 리랭커가 뒤에 있다면 순서 지표(nDCG·MRR)는 리랭커 이후에 봅니다.
- LLM-as-judge는 유용하지만 **사람 라벨과 일치율을 먼저 측정**한 뒤 써야 합니다. 검증 없는 저지는 그냥 또 하나의 추측입니다.
- CI 게이트는 **절대 점수가 아니라 이전 커밋 대비 하락폭**으로 거십시오.

## 1. 왜 평가부터 만들어야 하는가

RAG 시스템을 3개월 운영해 본 팀은 대부분 같은 곳에 도착합니다. 청크 크기를 바꾸고, 임베딩 모델을 갈아끼우고, 리랭커를 붙이고, 프롬프트를 다듬었는데 — **지금이 3개월 전보다 나은지 말할 수 없습니다.**

원인은 단순합니다. 변경마다 확인한 것이 "질문 몇 개 던져보니 좋아 보였다"였기 때문입니다. 이 방식에는 세 가지 결함이 있습니다.

- **표본이 매번 다릅니다.** 사람은 자기가 방금 고친 부분을 건드리는 질문을 무의식적으로 고릅니다
- **회귀가 안 보입니다.** 새 기능이 좋아지는 동안 기존에 잘 되던 10개가 깨져도 그 10개를 다시 던져보지 않습니다
- **되돌릴 근거가 없습니다.** 나빠진 것 같은데 어느 커밋부터인지 특정할 수 없으면 롤백도 못 합니다

> 💡 평가 파이프라인의 가치는 "품질을 올린다"가 아니라 **"품질 변화를 관측 가능하게 만든다"** 입니다. 관측되지 않는 것은 관리되지 않습니다.

순서도 중요합니다. **평가를 먼저 만들고 튜닝하십시오.** 튜닝을 먼저 하면, 나중에 만든 골든 셋이 이미 튜닝된 방향으로 편향됩니다. 자기가 맞춘 문제로 시험을 보는 셈입니다.

## 2. 무엇을 평가하는가 — 두 단계를 분리하라

RAG는 최소 두 단계입니다.

```
질문 → [검색] → 문서 k개 → [생성] → 답변
         ↑                      ↑
    Recall@k 등            Faithfulness 등
```

최종 답변만 채점하면 **실패 원인을 알 수 없습니다.** 답이 틀렸을 때 가능성은 두 가지입니다.

| 실패 유형 | 증상 | 조치 |
| --- | --- | --- |
| 검색 실패 | 정답 문서가 k개 안에 없음 | 임베딩·하이브리드·청킹 손봄 |
| 생성 실패 | 정답 문서는 있는데 답이 틀림 | 프롬프트·컨텍스트 배치·모델 손봄 |

두 실패의 처방은 완전히 다릅니다. 그런데 최종 답변만 보면 **검색을 고쳐야 할 상황에 프롬프트를 만지게 됩니다.** 실제로 가장 흔한 낭비가 이것입니다.

그래서 파이프라인은 반드시 두 층으로 만듭니다.

1. **검색 평가** — 질문과 정답 문서 ID만 있으면 되고, LLM 호출이 없어 **싸고 빠릅니다**. 매 커밋마다 돌릴 수 있습니다
2. **생성 평가** — LLM 호출이 필요해 느리고 비쌉니다. 야간 배치나 릴리스 전에만 돌립니다

이 분리는 비용 구조 때문에도 필수입니다. 검색 평가 200건은 몇 초에 끝나고 돈이 안 듭니다. 생성 평가 200건은 저지 모델 호출까지 포함해 수십 분과 실제 비용이 듭니다.

## 3. 골든 셋 — 질문을 어디서 구하는가

골든 셋은 `(질문, 정답 문서 ID들, 기준 답변)` 세 쌍의 모음입니다. 질문 확보 경로는 네 가지이고, 우선순위가 뚜렷합니다.

**1순위 — 실제 사용자 로그.** 가장 가치 있습니다. 실제 분포를 반영하고, 사람이 상상하지 못하는 표현(오타, 반말, 줄임말, 두 질문 붙여 쓰기)이 들어 있습니다. 서비스 중이라면 여기서 시작하십시오.

**2순위 — 고객 지원 티켓·사내 Q&A.** 아직 서비스 전이라면 차선책입니다. 실제 사람이 실제로 궁금해한 것이라는 점에서 합성 질문보다 낫습니다.

**3순위 — 도메인 전문가 작성.** 커버리지 구멍을 메울 때 유용합니다. 다만 전문가는 **전문가처럼 질문**하므로 실사용자보다 어휘가 정확합니다. 이것만으로 구성하면 실제 난이도를 과소평가하게 됩니다.

**4순위 — LLM 합성 질문.** 문서를 주고 "이 문단으로 답할 수 있는 질문을 만들어라"로 뽑습니다. 부트스트랩에는 훌륭하지만 두 가지 편향이 있습니다. 문서 표현을 그대로 베껴 **어휘 불일치가 없고**(그래서 BM25가 실제보다 좋아 보입니다), 한 문단으로 답할 수 있는 **단문 질문에 치우칩니다.**

> ⚠️ 합성 질문만으로 만든 골든 셋에서 하이브리드 검색이 별 효과 없어 보이는 일이 흔합니다. 합성 질문은 문서와 같은 단어를 쓰기 때문에 어휘 검색이 이미 잘 맞습니다. 실제 사용자는 다른 단어로 묻습니다.

현실적인 조합은 **로그 60% + 전문가 25% + 합성 15%** 정도입니다. 서비스 전이라면 합성으로 시작하되, 오픈 후 2주 안에 로그로 절반 이상을 교체할 계획을 세워두십시오.

## 4. 골든 셋 — 크기와 분포

가장 많이 받는 질문이 "몇 개나 필요한가"입니다.

| 규모 | 용도 | 비고 |
| --- | --- | --- |
| 30~50 | 스모크 테스트 | 큰 회귀만 잡힘. 5%p 차이는 노이즈 |
| 100~150 | 실용 최소선 | 대부분의 팀에 적정. 커밋 게이트로 충분 |
| 300~500 | 세분화 분석 | 카테고리별로 쪼개 봐도 통계가 남음 |
| 1,000+ | 모델 비교·논문 | 유지 비용이 급격히 커짐 |

**150개가 실용적인 목표점입니다.** 중요한 것은 크기가 아니라 분포입니다. 150개가 전부 "정의를 묻는 단문"이면 3,000개짜리 편향 셋과 다를 바 없습니다.

최소한 이 축들로 쿼터를 정해두십시오.

- **난이도** — 단일 문서로 답 가능 / 여러 문서 종합 필요 / 답이 없음(거절해야 함)
- **질문 유형** — 사실 조회, 절차 설명, 비교, 수치 확인, 예외 상황
- **길이** — 키워드 두 단어짜리부터 세 문장짜리까지
- **시점** — 최신 문서만 답할 수 있는 질문 포함(문서 갱신 반영 여부를 잡습니다)

**"답이 없음" 케이스를 반드시 넣으십시오.** 전체의 10~15%가 적당합니다. 이게 없으면 시스템이 아무거나 그럴듯하게 지어내는 성향을 전혀 측정하지 못합니다. 실무에서 사고를 내는 것은 대개 이쪽입니다.

## 5. 라벨링 — 정답 문서를 붙이는 실전 요령

질문마다 "이 문서가 답을 담고 있다"는 문서 ID 목록이 필요합니다. 전체 코퍼스를 사람이 훑을 수는 없으므로 **풀링(pooling)** 을 씁니다.

1. 여러 검색기(BM25, 임베딩, 하이브리드)로 각각 상위 20개를 뽑습니다
2. 합집합을 만듭니다 — 보통 질문당 30~50개
3. 사람이 그 후보만 보고 관련/비관련을 판정합니다

전수 조사 대비 노동량이 수십 분의 일로 줄고, 실무 정확도는 충분합니다. **주의점은 풀에 없는 문서가 영원히 비관련으로 남는다는 것**입니다. 그래서 풀을 만들 때 **성격이 다른 검색기를 섞어야** 합니다. 임베딩 세 개로 풀링하면 셋 다 놓치는 문서가 통째로 사라집니다.

판정은 이진보다 **3단계**를 권합니다.

- `2` — 이 문서만으로 답할 수 있음
- `1` — 부분적으로 관련. 다른 문서와 합쳐야 답이 됨
- `0` — 무관

nDCG를 쓸 때 등급이 필요하고, "부분 관련"을 0으로 밀면 여러 문서 종합형 질문의 점수가 실제보다 나쁘게 나옵니다.

**저장 포맷은 JSONL이 편합니다.** 한 줄에 한 케이스, diff가 읽히고 부분 수정이 쉽습니다.

```jsonl
{"qid":"q-0031","question":"환불 신청은 결제 후 며칠까지 가능한가요?","category":"policy","difficulty":"single","relevant":[{"doc_id":"faq-refund-01","grade":2},{"doc_id":"tos-07","grade":1}],"reference_answer":"결제일로부터 7일 이내...","source":"log","added":"2026-08-30"}
{"qid":"q-0032","question":"작년 4분기 매출 성장률","category":"finance","difficulty":"multi","relevant":[{"doc_id":"ir-2025q4","grade":2},{"doc_id":"ir-2025q3","grade":2}],"reference_answer":"...","source":"expert","added":"2026-08-30"}
{"qid":"q-0033","question":"경쟁사 내부 마진율 알려주세요","category":"policy","difficulty":"unanswerable","relevant":[],"reference_answer":null,"source":"log","added":"2026-08-30"}
```

`source`와 `added` 필드를 빼먹지 마십시오. 나중에 "로그 질문 비율이 얼마나 되나", "6개월 넘은 케이스가 몇 개나 남아 있나"를 물어야 할 때가 반드시 옵니다. 그때 필드가 없으면 전수 재검토밖에 방법이 없습니다.

> 📎 라벨은 **문서 ID가 아니라 청크 ID**로 붙이는 편이 낫습니다. 다만 청킹 전략을 바꾸면 라벨이 무효화됩니다. 청킹을 자주 실험할 계획이라면 문서 ID로 붙이고, 청크→문서 매핑으로 채점하십시오. 이 선택은 나중에 바꾸기 어렵습니다.

## 6. 검색 단계 지표 — 무엇을 1순위로 볼 것인가

```python
def recall_at_k(retrieved_ids, relevant_ids, k):
    """정답 문서 중 몇 %를 상위 k개 안에 데려왔는가"""
    top_k = set(retrieved_ids[:k])
    if not relevant_ids:
        return None            # '답 없음' 케이스는 별도 집계
    return len(top_k & set(relevant_ids)) / len(relevant_ids)


def mrr(retrieved_ids, relevant_ids):
    """첫 정답이 몇 번째에 나오는가의 역수"""
    for i, doc_id in enumerate(retrieved_ids, start=1):
        if doc_id in relevant_ids:
            return 1.0 / i
    return 0.0
```

| 지표 | 답하는 질문 | 언제 보는가 |
| --- | --- | --- |
| **Recall@k** | 정답이 후보 안에 들어왔는가 | **1순위.** 리랭커 앞단 평가 |
| MRR | 첫 정답이 얼마나 위인가 | 사용자가 1건만 보는 UI |
| nDCG@k | 순서가 얼마나 이상적인가 | 리랭커 **이후** 순서 품질 |
| Precision@k | 후보 중 잡음 비율 | 컨텍스트 토큰 예산이 빡빡할 때 |

**왜 Recall@k가 1순위인가.** 검색이 못 데려온 문서는 뒤에서 무엇을 해도 복구되지 않습니다. 리랭커는 후보 안에서 순서를 바꿀 뿐 없는 문서를 만들어내지 못합니다. **Recall@k는 파이프라인 전체 성능의 천장**입니다.

그래서 실무 구성은 이렇게 갑니다.

- 검색기는 `k=50~100`으로 넓게 뽑아 **Recall@50을 최대화**
- 리랭커가 그중 상위 5~10개로 좁힘 — 여기서 **nDCG@10**을 봄
- 최종 컨텍스트에 들어가는 개수 기준으로 **Precision** 확인

Recall@50이 0.75인데 nDCG@10을 아무리 올려도 나머지 25%는 영영 못 답합니다. 순서 지표부터 손대는 것은 **천장이 낮은 상태에서 천장 아래를 정리하는 일**입니다.

## 7. 생성 단계 지표 — 그리고 LLM-as-judge의 함정

생성 단계에서 실무적으로 필요한 것은 세 가지입니다.

- **Faithfulness(충실성)** — 답변의 각 주장이 제공된 컨텍스트로 뒷받침되는가. **환각을 직접 잡는 지표**입니다
- **Answer Relevancy(관련성)** — 답변이 질문에 실제로 답하는가. 맞는 말이지만 딴소리인 경우를 잡습니다
- **거절 정확도** — 답이 없을 때 "모른다"고 하는가. 4장에서 넣어둔 "답 없음" 케이스로 측정합니다

이 지표들은 대개 LLM에게 채점을 시킵니다. 여기서 가장 큰 함정이 나옵니다.

> ⚠️ **저지 모델을 검증 없이 신뢰하면 안 됩니다.** 저지도 LLM이므로 틀립니다. 그리고 그 오류는 무작위가 아니라 **체계적으로 한쪽으로 쏠립니다** — 길고 자신 있는 문장을 높게 주고, 짧고 조심스러운 답을 낮게 줍니다. 자기 계열 모델이 쓴 답을 후하게 주는 경향도 보고돼 있습니다.

그래서 저지를 도입할 때는 반드시 이 순서를 밟으십시오.

1. 사람이 **50건 정도를 직접 채점**합니다
2. 같은 50건을 저지에게 채점시킵니다
3. **일치율(또는 Cohen's kappa)** 을 계산합니다
4. 일치율이 낮으면 저지 프롬프트를 고치고 다시 2번으로

일치율이 납득할 수준(이진 판정 기준 대략 80% 이상)에 오르기 전에는 저지 점수를 **의사결정에 쓰지 마십시오.** 그 전까지 저지 점수는 지표가 아니라 또 하나의 추측입니다.

저지 프롬프트를 안정시키는 실전 요령입니다.

- **1~5점 척도보다 이진 판정**이 훨씬 안정적입니다. "이 주장이 컨텍스트로 뒷받침되는가: 예/아니오"
- 답변을 **주장 단위로 쪼갠 뒤** 각각 판정하고 비율을 냅니다. 통짜 채점은 재현성이 낮습니다
- 판정 **근거를 먼저 쓰게** 하고 결론을 뒤에 두십시오
- `temperature=0`으로 고정하고, 저지 모델 버전을 **기록**하십시오. 저지가 바뀌면 과거 점수와 비교 불가입니다

## 8. 회귀 테스트로 만들기 — CI에 넣는 구조

지표를 계산할 수 있게 됐으면 이제 자동화입니다. 핵심은 **결과를 매번 저장하고 이전과 비교**하는 것입니다.

```python
# eval/run.py — 요지만
import json, datetime

def evaluate(pipeline, golden_set, k=50):
    rows = []
    for case in golden_set:
        hits = pipeline.retrieve(case["question"], k=k)
        ids = [h.doc_id for h in hits]
        rows.append({
            "qid": case["qid"],
            "category": case["category"],
            "recall_at_k": recall_at_k(ids, case["relevant_ids"], k),
            "mrr": mrr(ids, case["relevant_ids"]),
        })
    scored = [r for r in rows if r["recall_at_k"] is not None]
    return {
        "commit": current_commit(),
        "ts": datetime.datetime.now().isoformat(),
        "n": len(scored),
        "recall_at_k": sum(r["recall_at_k"] for r in scored) / len(scored),
        "mrr": sum(r["mrr"] for r in scored) / len(scored),
        "rows": rows,          # 케이스별 원본 — 이게 진짜 자산입니다
    }
```

**케이스별 원본 행을 반드시 남기십시오.** 평균만 저장하면 "0.81에서 0.78로 떨어졌다"까지만 알 수 있습니다. 행이 있으면 **어느 질문이 깨졌는지** 바로 diff할 수 있고, 그게 디버깅 시간의 대부분을 줄여줍니다.

게이트는 이렇게 겁니다.

```yaml
# .github/workflows/rag-eval.yml — 요지
- run: python eval/run.py --out results/current.json
- run: python eval/compare.py --base results/main.json --head results/current.json
```

```python
# eval/compare.py — 판정 규칙
DROP_TOLERANCE = 0.02          # 평균 2%p까지는 노이즈로 허용
MAX_NEWLY_BROKEN = 3           # 이전엔 맞았는데 이번에 깨진 케이스 허용치

def gate(base, head):
    fails = []
    if head["recall_at_k"] < base["recall_at_k"] - DROP_TOLERANCE:
        fails.append(f"recall {base['recall_at_k']:.3f} → {head['recall_at_k']:.3f}")

    prev = {r["qid"]: r["recall_at_k"] for r in base["rows"]}
    broken = [r["qid"] for r in head["rows"]
              if prev.get(r["qid"], 0) > 0 and (r["recall_at_k"] or 0) == 0]
    if len(broken) > MAX_NEWLY_BROKEN:
        fails.append(f"newly broken: {broken}")
    return fails
```

> 💡 **절대 점수로 게이트를 걸지 마십시오.** "Recall@50 ≥ 0.80"으로 걸면 기준선이 0.79인 팀은 첫날부터 CI가 빨간불이고, 결국 게이트를 꺼버립니다. **이전 커밋 대비 하락폭**으로 걸어야 실제로 살아남습니다.

`MAX_NEWLY_BROKEN`이 특히 중요합니다. 평균은 그대로인데 **맞던 5개가 깨지고 틀리던 5개가 맞는** 교환이 일어날 수 있습니다. 평균만 보면 이 변화가 보이지 않습니다.

실행 주기는 비용에 맞춰 나눕니다.

| 시점 | 무엇을 | 소요 |
| --- | --- | --- |
| 매 PR | 검색 평가 전체 | 수십 초, 비용 0 |
| 야간 | 생성 평가 전체 | 수십 분, 저지 비용 발생 |
| 릴리스 전 | 둘 다 + 카테고리별 분해 | — |

## 9. 골든 셋 유지보수 — 썩는 것을 막는다

만들고 끝이 아닙니다. 골든 셋은 **썩습니다.**

- **문서가 갱신됩니다.** 정답 문서가 개정되거나 삭제되면 라벨이 틀린 것이 됩니다. 문서 ID 유효성 검사를 CI에 같이 넣으십시오. 정답 ID가 코퍼스에 없으면 실패시킵니다
- **질문 분포가 이동합니다.** 신규 기능이 나오면 사용자 질문이 그쪽으로 몰립니다. **분기마다 로그에서 20~30개를 새로 뽑아 교체**하는 리듬을 권합니다
- **셋에 과적합됩니다.** 몇 달간 같은 150개만 보면 그 150개에 맞춰 튜닝하게 됩니다. **홀드아웃 30개는 잠가두고** 릴리스 전에만 열어보십시오

- **사람이 틀리게 라벨한 것이 남습니다.** 점수가 유독 나쁜 케이스는 시스템이 아니라 **라벨이 틀린** 경우가 꽤 됩니다. 분기 점검 때 하위 10개 케이스는 라벨부터 다시 보십시오

**오염(contamination)** 도 실질적인 문제입니다. 골든 셋 질문과 기준 답변을 프롬프트 예시로 쓰면 그 질문에서 점수가 부풀려집니다. 평가 데이터는 **저장소를 분리하거나 최소한 디렉터리를 분리**하고, 프롬프트에서 참조하지 않는다는 규칙을 명시해두십시오.

## 10. 흔한 실수 여섯 가지

| 실수 | 왜 문제인가 | 대신 |
| --- | --- | --- |
| 최종 답변만 채점 | 검색 실패와 생성 실패를 구분 못 함 | 두 단계 분리 측정 |
| 합성 질문만으로 구성 | 어휘 불일치가 없어 검색이 과대평가됨 | 로그 질문을 절반 이상 |
| "답 없음" 케이스 누락 | 환각 성향이 전혀 측정되지 않음 | 전체의 10~15% 확보 |
| 평균만 저장 | 어느 케이스가 깨졌는지 모름 | 케이스별 행 보존 |
| 절대 점수 게이트 | 첫날부터 빨간불 → 게이트 폐기 | 이전 대비 하락폭 |
| 저지 검증 없이 신뢰 | 체계적 편향이 그대로 반영됨 | 사람 50건과 일치율 먼저 |

## 마무리 — 어디서부터 시작할까

한 번에 다 만들 필요 없습니다. 순서는 이렇습니다.

1. **로그에서 질문 50개**를 뽑습니다. 없으면 합성으로 시작하되 교체 계획을 세웁니다
2. 풀링으로 **정답 문서를 라벨링**합니다. 반나절이면 끝납니다
3. **Recall@50 스크립트**를 만들고 지금 값을 기록합니다 — 이게 기준선입니다
4. **CI에 붙이고 하락폭 게이트**를 겁니다. 여기까지가 1주일 작업입니다
5. 그다음에야 생성 평가와 저지를 붙입니다

3번까지만 해도 대부분의 회귀는 잡힙니다. 그리고 이 지점을 지나면 앞선 글들에서 다룬 하이브리드 검색·리랭커·임베딩 교체가 **"좋아 보인다"가 아니라 "Recall@50이 0.74에서 0.83으로 올랐다"** 로 바뀝니다. 그 차이가 3개월 뒤의 시스템을 결정합니다.

# RAG Reranker 완전정리 — Bi-Encoder·Cross-Encoder 2단계 검색 설계

검색 로그에서 자주 마주치는 장면이 있습니다. 정답 문서가 Top-50 안에는 분명히 들어와 있는데 Top-5 밖에 있어서, LLM에 넘기는 최종 컨텍스트에는 끝내 포함되지 않습니다. 앞선 글에서 Hybrid Search로 후보 품질을 끌어올리는 방법을 다뤘는데, 그렇게 넉넉히 뽑은 후보 중에서 **정말 답이 되는 소수를 골라내는 단계**가 오늘의 주제입니다. 이 정렬 문제는 검색기를 아무리 바꿔도 풀리지 않습니다. 애초에 검색기가 순위를 매기는 방식에 한계가 있기 때문입니다.

## 핵심 요약

- 검색(retrieval)과 재순위화(reranking)는 **다른 문제**입니다. 검색은 방대한 문서에서 후보를 빠르게 좁히고, 재순위화는 그 좁은 후보를 **정밀하게 다시 줄 세웁니다**.
- Bi-Encoder는 질문과 문서를 **따로** 임베딩해 벡터 유사도로 비교하고, Cross-Encoder는 질문과 문서를 **함께** 넣어 상호작용까지 읽습니다. 정확도는 Cross-Encoder가, 속도는 Bi-Encoder가 이깁니다.
- 그래서 실무 표준은 **2단계**입니다. Bi-Encoder(또는 Hybrid)로 Top-N을 빠르게 뽑고, Cross-Encoder 리랭커로 그 N개만 정밀 재정렬해 Top-k를 만듭니다.
- 리랭커는 **문서 수에 비례하는 추론 비용**을 지불합니다. N을 무한정 키울 수 없으므로, 검색이 정답을 Top-N 안에 넣어주는 것이 전제 조건입니다.
- 리랭커를 켜기 전과 후를 **같은 골든 셋으로 nDCG·Hit@k를 비교**하십시오. 후보에 정답이 없으면 리랭커는 아무것도 구제하지 못합니다.

## 1. 검색과 재순위화는 다른 문제다 — 역할부터 구분

리랭커를 붙이기 전에, 그것이 검색기와 무엇이 다른지부터 정리해야 합니다. 둘을 같은 것으로 보면 잘못된 곳을 튜닝하게 됩니다.

| 축 | 1단계 검색(Retrieval) | 2단계 재순위화(Reranking) |
|---|---|---|
| 대상 | 전체 문서(수십만~수억) | 검색이 좁힌 후보(수십~수백) |
| 목표 | Recall — 정답을 놓치지 않기 | Precision — 상위에 정답을 몰기 |
| 방식 | 벡터 근접성·키워드 매칭 | 질문·문서 상호작용 정밀 판정 |
| 속도 | 밀리초 단위(사전 계산된 인덱스) | 후보 수에 비례(실시간 추론) |
| 지표 | Recall@50, Hit@50 | nDCG@10, MRR, Hit@5 |

핵심은 **판정 기준이 다르다**는 것입니다. 1단계는 "정답이 후보에 들어왔는가(Recall)"만 책임지면 되고, 2단계는 "그 후보 중 정답이 맨 위에 있는가(Precision)"를 책임집니다. Query Transformation 글의 진단 코드에서 `hit@50`은 높은데 `hit@5`가 낮은 경우가 바로 이 재순위화가 필요한 신호였습니다.

> 리랭커는 검색의 상위 호환이 아닙니다. 검색이 놓친 문서는 리랭커가 되살릴 수 없습니다. 리랭커는 후보 안에서만 순서를 바꿉니다. 그래서 항상 **Recall 좋은 검색 + Precision 좋은 리랭커**의 조합으로 설계합니다.

## 2. Bi-Encoder — 빠른 대신 상호작용을 못 본다

Bi-Encoder는 이름 그대로 인코더를 두 번 따로 돌립니다. 질문을 벡터로, 문서를 벡터로 각각 변환한 뒤 코사인 유사도로 비교합니다.

```python
# Bi-Encoder: 질문과 문서를 독립적으로 임베딩
q_vec = encoder.encode(query)          # 질문 벡터 1개
doc_vecs = encoder.encode(documents)   # 문서 벡터들 (사전 계산 가능)
scores = cosine_similarity(q_vec, doc_vecs)
```

이 구조의 결정적 강점은 **문서 벡터를 미리 계산해 인덱스에 저장할 수 있다**는 점입니다. 질문이 들어오면 질문만 임베딩하고 나머지는 벡터 검색으로 끝나므로, 수억 건에서도 밀리초 안에 후보를 뽑습니다. Dense 검색이 바로 이 방식이고, RAG의 1단계는 사실상 전부 Bi-Encoder입니다.

한계도 이 구조에서 나옵니다. 질문과 문서가 **각자 벡터로 압축된 뒤에야 만나기** 때문에, "질문의 이 단어가 문서의 저 문장과 대응한다" 같은 세밀한 상호작용이 벡터 하나로 뭉개집니다. 부정어·조건·고유명사처럼 국소적인 신호가 평균에 묻히는 이유가 이것입니다.

## 3. Cross-Encoder — 정확한 대신 미리 계산할 수 없다

Cross-Encoder는 질문과 문서를 **하나의 입력으로 이어 붙여** 모델에 통과시킵니다. 트랜스포머의 셀프 어텐션이 질문 토큰과 문서 토큰을 직접 교차시켜, 둘 사이의 관련성을 하나의 점수로 출력합니다.

```python
# Cross-Encoder: (질문, 문서) 쌍을 함께 입력
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")
pairs = [(query, doc.text) for doc in candidates]
scores = reranker.predict(pairs)   # 각 쌍마다 forward pass 1회
```

정확도가 높은 이유는 명확합니다. 질문과 문서가 **압축되기 전에** 어텐션으로 만나므로, Bi-Encoder가 잃어버린 국소 상호작용을 그대로 봅니다. 같은 후보 집합에서 Cross-Encoder가 Bi-Encoder보다 상위 정렬 품질이 높다는 것은 여러 벤치마크에서 반복적으로 확인됩니다.

대가는 **사전 계산이 불가능**하다는 점입니다. 점수는 (질문, 문서) 쌍마다 새로 계산해야 하므로, 문서 벡터를 미리 저장해 두는 트릭을 쓸 수 없습니다. 후보가 N개면 forward pass가 N번 돕니다. 이 비용 때문에 Cross-Encoder를 전체 문서에 돌리는 것은 불가능하고, **검색이 좁혀준 후보에만** 씁니다.

숫자로 감을 잡아 두면 설계가 쉬워집니다. Bi-Encoder는 문서 100만 건을 색인 시점에 한 번 임베딩해 두면, 질의 시점에는 질문 벡터 1개만 만들고 나머지는 근사 최근접 탐색(ANN)으로 끝냅니다. Cross-Encoder는 정반대입니다. 색인 시점에 미리 할 수 있는 일이 없고, 질의마다 후보 수만큼 모델을 돌립니다. 그래서 "전체를 Cross-Encoder로 검색한다"는 발상은 100만 번의 forward pass를 뜻해 성립하지 않습니다. 두 인코더의 역할이 갈리는 지점이 바로 이 계산 시점의 비대칭입니다.

## 4. 2단계 설계 — 검색으로 좁히고 리랭커로 세운다

두 인코더의 장단점이 정확히 상보적이므로, 실무는 둘을 파이프라인으로 잇습니다.

```text
질문
 ├─ Hybrid Search (Dense + BM25 → RRF)  Top-N (예: 50~100)
 │                                         ↓
 └───────────────────────────────  Cross-Encoder 리랭커  Top-k (예: 5) → LLM
```

이 설계의 핵심 파라미터는 **N(리랭커에 넘기는 후보 수)** 하나입니다.

- **N이 작으면** 리랭커가 빠르지만, 1단계가 정답을 N 밖으로 밀어냈다면 리랭커가 손쓸 방법이 없습니다.
- **N이 크면** 정답이 후보에 들어올 확률은 올라가지만, forward pass가 N번이라 지연시간이 선형으로 늘어납니다.

적정 N은 도메인마다 다르므로 골든 셋으로 정해야 합니다. **1단계의 Recall@N 곡선을 그려서, Recall이 포화되는 지점을 N으로 잡는 것**이 원칙입니다. Recall@50과 Recall@100이 거의 같다면 굳이 100개를 리랭킹할 이유가 없습니다.

```python
# N 후보를 검색해 리랭커로 Top-k 재정렬하는 최소 구성
def retrieve_and_rerank(query, retriever, reranker, n=50, k=5):
    candidates = retriever.search(query, k=n)          # 1단계: 넉넉히
    pairs = [(query, c.text) for c in candidates]
    scores = reranker.predict(pairs)                    # 2단계: 정밀 재정렬
    ranked = sorted(zip(candidates, scores),
                    key=lambda x: x[1], reverse=True)
    return [c for c, s in ranked[:k]]                   # 상위 k개만 LLM으로
```

## 5. 모델 선택 — 오픈소스·API·ColBERT의 3갈래

리랭커는 크게 세 갈래로 나뉩니다. 운영 제약(GPU 보유 여부, 지연시간 예산, 데이터 반출 정책)에 따라 고릅니다.

| 갈래 | 대표 | 특징 | 적합한 상황 |
|---|---|---|---|
| 오픈소스 Cross-Encoder | BGE-reranker-v2, Jina Reranker, mxbai-rerank | GPU에 직접 서빙, 데이터 외부 반출 없음 | GPU가 있고 온프레미스가 필요할 때 |
| API Cross-Encoder | Cohere Rerank 3.5 | 인프라 부담 없음, 다국어 강함 | 초기 도입·트래픽이 불규칙할 때 |
| Late Interaction | ColBERT, ColBERTv2 | Bi와 Cross의 중간, 토큰 단위 지연 상호작용 | 정확도와 속도의 절충이 필요할 때 |

- **오픈소스 Cross-Encoder** — `BAAI/bge-reranker-v2-m3`는 다국어를 포함해 널리 쓰이는 기본값입니다. GPU 한 장에 올려 배치로 돌리면 API 왕복 없이 처리됩니다. 한국어 문서라면 다국어 리랭커를 고르되, 반드시 자체 골든 셋으로 성능을 확인하십시오.
- **API Cross-Encoder** — Cohere Rerank 3.5(2024년 12월)는 문서당 컨텍스트 4096토큰을 지원하고 다국어 검색에서 강합니다. 인프라를 두지 않아도 되는 대신, 문서를 외부로 보내는 것이 정책상 가능한지 먼저 확인해야 합니다.
- **Late Interaction(ColBERT)** — 질문과 문서를 토큰 단위 벡터로 저장해 두고, 검색 시점에 토큰끼리 지연 상호작용(late interaction)을 계산합니다. Cross-Encoder만큼 무겁지 않으면서 Bi-Encoder보다 정밀합니다. 다만 토큰 단위 벡터를 저장해야 해서 인덱스 용량이 커집니다.

모델을 고를 때 벤치마크 점수만 보고 결정하지 마십시오. 리더보드 상위 모델이 우리 도메인에서도 1위라는 보장은 없습니다. 법률·의료·사내 문서처럼 일반 코퍼스와 어휘가 다른 영역에서는, 벤치마크 3위 모델이 우리 골든 셋에서 1위가 되는 일이 흔합니다. 후보를 2~3개로 좁힌 뒤에는 반드시 **자체 골든 셋으로 리랭킹 전후를 직접 측정**해 최종 선택하십시오. 여기에 더해 모델 크기도 함께 저울질해야 합니다. 큰 리랭커가 정확도는 높아도 지연이 예산을 넘기면 서비스에서는 쓸 수 없기 때문입니다.

## 6. 지연시간과 비용 — 리랭커는 후보 수만큼 비싸다

리랭커의 비용 구조는 단순합니다. **후보 N개 = forward pass N회**입니다. 이 선형성을 이해하면 어디를 조절할지 보입니다.

- **GPU 서빙(오픈소스)** — 지연시간은 배치 크기와 시퀀스 길이에 좌우됩니다. N개 쌍을 한 배치로 묶어 GPU에 한 번에 태우면, N을 낱개로 처리할 때보다 훨씬 빠릅니다. 문서를 리랭커의 최대 입력 길이에 맞춰 자르는 것도 지연을 줄입니다.
- **API 과금(Cohere 등)** — 검색 1회(질문 + 후보 묶음)가 과금 단위입니다. 후보가 많거나 문서가 길어 내부적으로 여러 청크로 쪼개지면 과금이 늘어납니다. Cohere API는 `문서 수 × max_chunks_per_doc`가 10,000 미만이어야 한다는 제약을 두고 있는데, 이는 곧 **문서가 길수록 청크가 늘어 비용과 제약에 함께 걸린다**는 뜻입니다.

실무 절감 요령은 세 가지입니다.

- **N을 골든 셋으로 최소화** — Recall이 포화되는 지점 이상으로 후보를 넘기지 마십시오.
- **입력 길이 제한** — 리랭커에 문서 전체가 아니라 관련 청크만 넣습니다. 청킹 글에서 다룬 경계 설계가 여기서도 효과를 냅니다.
- **캐싱** — 같은 (질문, 문서) 쌍이 반복되는 서비스라면 점수를 캐시해 재계산을 없앱니다.

> 리랭커를 붙이면 TTFT(첫 토큰까지 시간)가 늘어납니다. 검색·리랭킹·생성 전체의 지연 예산을 먼저 정하고, 그 안에서 N을 정하십시오. "정확도가 오르니까 무조건 켠다"는 접근은 지연 예산을 넘겨 사용자 경험을 해칩니다.

## 7. 점수 다루기 — 리랭커 점수는 보정되어 있지 않다

리랭커가 출력하는 점수는 **순서를 매기는 용도**이지, 절대적 신뢰도가 아닙니다. 여기서 흔한 사고가 납니다.

- Cross-Encoder 점수의 범위와 분포는 모델마다 다릅니다. 어떤 모델은 로짓(logit)을, 어떤 모델은 시그모이드를 통과한 0~1 값을 줍니다.
- 그래서 `점수 > 0.5`처럼 **고정 임계값으로 문서를 버리는 로직은 모델을 바꾸면 깨집니다.**

임계값으로 무관한 문서를 걸러내고 싶다면, 절대값이 아니라 **골든 셋에서 임계값을 직접 보정**해야 합니다. 정답 문서의 점수 분포와 오답 문서의 점수 분포를 그려서, 둘을 가르는 지점을 임계값으로 잡습니다. 그마저도 모델·도메인이 바뀌면 다시 잡아야 합니다.

```python
# 고정 임계값 대신, 상위 k개만 취하는 것이 이식성이 높다
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
top_k = [c for c, s in ranked[:k]]         # 순위 기반: 모델 바뀌어도 동작
# 임계값이 필요하면 골든 셋으로 보정한 값만 사용
kept = [c for c, s in ranked if s >= CALIBRATED_THRESHOLD]
```

## 8. 평가 — 리랭커가 정말 도움이 되는지 잰다

리랭커는 켜는 것이 시작이고, **켜서 좋아졌는지**가 본론입니다. Hybrid Search 글의 비교 코드를 확장해, 리랭킹 전후를 나란히 놓습니다.

```python
def eval_reranking(golden_set, retriever, reranker, n=50, k=5):
    stats = {"before": [], "after": []}
    for q, gold_ids in golden_set:
        cands = retriever.search(q, k=n)
        before = [c.id for c in cands][:k]                  # 검색 원순위 Top-k
        scores = reranker.predict([(q, c.text) for c in cands])
        after = [c.id for c, s in
                 sorted(zip(cands, scores), key=lambda x: x[1], reverse=True)][:k]
        for name, ids in [("before", before), ("after", after)]:
            stats[name].append(float(any(g in ids for g in gold_ids)))
    return {k: sum(v) / len(v) for k, v in stats.items()}    # Hit@k 전후 비교
```

읽는 법이 중요합니다.

- **after가 before보다 확실히 높다** — 리랭커가 제 역할을 합니다. 도입 가치가 데이터로 확인됩니다.
- **after와 before가 거의 같다** — 1단계 순위가 이미 좋거나, 리랭커 모델이 이 도메인과 안 맞습니다. 후자라면 다른 리랭커를 시험하십시오.
- **after가 오히려 낮다** — 리랭커에 넣는 입력이 잘렸거나(문서가 최대 길이를 초과), 후보에 정답이 아예 없어(Recall@N 부족) 리랭커가 오답끼리 정렬한 경우입니다.

정렬 품질을 세밀히 보려면 Hit@k만이 아니라 **nDCG@10**을 함께 재십시오. Hit@k는 정답이 상위 k개 안에 들어왔는지만 0/1로 보지만, nDCG는 정답이 **몇 위에 오는지**까지 로그 가중으로 반영합니다. 그래서 "Top-5 안에는 이미 있었지만 5위에서 2위로 올라갔다" 같은 개선을 Hit@5는 놓치고 nDCG@10은 잡아냅니다. 리랭커의 진짜 기여는 이 순위 상승에 있으므로, 도입 효과를 과소평가하지 않으려면 두 지표를 함께 보아야 합니다.

## 9. 서빙 — GPU·배치·폴백 설계

리랭커를 운영에 얹으면 세 가지를 설계해야 합니다.

- **배치 처리** — N개 쌍을 낱개로 추론하지 말고 한 배치로 묶으십시오. GPU는 배치에서 처리량이 크게 오릅니다. 다만 배치가 너무 크면 지연이 튀므로, 지연 예산 안에서 배치 크기를 정합니다.
- **폴백 경로** — 리랭커(특히 API)가 실패하거나 지연이 예산을 넘기면, **1단계 검색 순위를 그대로 쓰는 폴백**을 두십시오. 리랭커가 죽었다고 검색 전체가 멈추면 안 됩니다.
- **관찰성** — 질문·검색 Top-N·리랭킹 후 Top-k·최종 인용을 로그로 남기십시오. 앞선 글들과 같은 원칙입니다. 리랭킹 전후 순위를 함께 남기면, "리랭커 때문에 나빠졌다"는 신고를 재현할 수 있습니다.

## 10. 흔한 실수

- **검색을 건너뛰고 리랭커만 강화한다** — 리랭커는 후보 안에서만 순서를 바꿉니다. Recall@N이 낮으면 리랭커를 아무리 좋은 걸로 바꿔도 개선되지 않습니다. 1단계 Recall을 먼저 보십시오.
- **N을 근거 없이 키운다** — 후보를 200개씩 리랭킹하면 지연만 늘고 정확도는 포화됩니다. Recall@N 곡선으로 포화 지점을 찾으십시오.
- **문서를 자르지 않고 통째로 넣는다** — 리랭커의 최대 입력을 넘기면 뒷부분이 잘려, 정작 정답 문장이 입력에서 빠집니다. 관련 청크만 넣으십시오.
- **고정 임계값으로 문서를 버린다** — 점수 분포는 모델마다 다릅니다. 임계값이 필요하면 골든 셋으로 보정하고, 아니면 상위 k개만 취하십시오.
- **리랭커 점수를 검색 점수와 더한다** — 둘은 스케일이 다릅니다. 리랭커를 썼으면 최종 순위는 리랭커 점수로만 정하십시오.
- **폴백 없이 API 리랭커에 의존한다** — 외부 API가 느려지거나 죽으면 검색 전체가 멈춥니다. 검색 원순위로 떨어지는 경로를 두십시오.
- **리랭킹 전후를 측정하지 않는다** — 도움이 되는지 모르는 채 지연만 늘리는 구성이 됩니다. 골든 셋으로 before/after를 반드시 재십시오.
- **다국어 문서에 영어 전용 리랭커를 쓴다** — 한국어 검색 품질이 무너집니다. 다국어 리랭커를 고르고 자체 데이터로 검증하십시오.

## 실전 체크리스트

- 1단계 검색의 Recall@N을 측정해, 정답이 후보에 들어오는지 먼저 확인했다.
- Recall@N 곡선을 그려 포화 지점을 N으로 잡았다.
- 리랭커에 넣는 문서를 최대 입력 길이 아래로 잘랐다(관련 청크만 투입).
- 오픈소스·API·ColBERT 중 운영 제약(GPU·반출 정책·지연 예산)에 맞는 갈래를 골랐다.
- 다국어 문서라면 다국어 리랭커를 선택하고 자체 골든 셋으로 검증했다.
- N개 쌍을 배치로 묶어 추론하도록 서빙을 구성했다.
- 리랭커 실패·지연 초과 시 1단계 순위로 떨어지는 폴백을 두었다.
- 문서 버리기가 필요하면 고정값이 아니라 골든 셋으로 보정한 임계값을 썼다.
- 골든 셋으로 리랭킹 전후 Hit@k·nDCG@10을 나란히 측정했다.
- 리랭킹 추가 지연을 TTFT 예산에 반영해 측정했다.
- 질문·검색 Top-N·리랭킹 후 Top-k·최종 인용을 로그로 남겼다.

## 마치며

리랭커는 검색을 더 똑똑하게 만드는 기술이 아니라, **검색이 넉넉히 뽑아준 후보를 정밀하게 줄 세우는 두 번째 렌즈**입니다. 그래서 리랭커의 성능은 언제나 1단계 검색의 Recall에 갇혀 있습니다. 후보에 없는 정답은 되살릴 수 없고, 후보에 있는 정답만 위로 끌어올립니다. 순서가 중요합니다. Recall 좋은 검색을 먼저 확보하고, 그 위에 Precision 좋은 리랭커를 얹는 것. 이 순서를 뒤집으면 비용만 내고 개선은 얻지 못합니다.

## FAQ

**Q1. 리랭커를 꼭 써야 하나요? Hybrid Search만으로는 부족한가요?**

질문 로그에 달렸습니다. Hybrid로 Hit@5가 충분히 높다면 리랭커 없이도 됩니다. 하지만 Hit@50은 높은데 Hit@5가 낮은 패턴이 보인다면, 그것이 바로 리랭커가 필요한 신호입니다. 후보에는 정답이 들어오는데 상위 정렬이 나쁜 상태이기 때문입니다.

**Q2. 오픈소스 리랭커와 Cohere 같은 API 중 무엇으로 시작해야 하나요?**

GPU가 이미 있고 데이터 반출이 제약이라면 오픈소스(BGE-reranker 등)로 시작하십시오. 인프라를 두기 부담스럽고 트래픽이 불규칙하다면 API가 낫습니다. 어느 쪽이든 **자체 골든 셋으로 리랭킹 전후를 측정**한 뒤 결정하는 것이 핵심입니다. 벤치마크 순위가 우리 도메인에서 재현된다는 보장은 없습니다.

**Q3. ColBERT는 리랭커인가요, 검색기인가요?**

둘 다로 쓸 수 있습니다. ColBERT는 토큰 단위 지연 상호작용(late interaction)으로, Bi-Encoder보다 정밀하고 Cross-Encoder보다 가볍습니다. 1단계 검색기로 쓰기도 하고, Bi-Encoder 검색 뒤 2단계 리랭커로 쓰기도 합니다. 정확도와 속도의 절충이 필요할 때 검토하는 중간 선택지입니다.

**Q4. 리랭커를 켰더니 오히려 답이 나빠졌습니다. 어디를 봐야 하나요?**

세 가지를 순서대로 보십시오. 첫째, 입력 길이 — 문서가 리랭커 최대 입력을 넘겨 잘렸는지 확인합니다. 둘째, Recall@N — 후보에 정답이 아예 없으면 리랭커는 오답끼리 정렬합니다. 셋째, 모델 적합성 — 다국어 문서에 영어 전용 리랭커를 썼거나, 도메인이 크게 다른 모델일 수 있습니다. 골든 셋으로 before/after를 재보면 어느 단계 문제인지 드러납니다.

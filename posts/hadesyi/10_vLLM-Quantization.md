# vLLM 양자화 완전정리 — GGUF·AWQ·GPTQ·W4A16·FP8 선택 기준

"GGUF로 받아서 vLLM에 올리면 되나요?" 로컬 LLM 서버를 세우다 보면 반드시 이 질문에 도착합니다. 답부터 말하면 **vLLM에서는 GGUF가 1순위가 아닙니다.** 공식 문서가 스스로 "매우 실험적이고 최적화가 덜 됐다"고 적어두고 있고, 아예 별도 플러그인으로 분리됐습니다. 그럼 무엇을 써야 하나. 이 글은 양자화 표기법을 읽는 법부터 GPU 세대별 정답, 실측 수치, KV 캐시라는 별도의 레버까지 실전 결정 순서대로 정리합니다.

## 핵심 요약

- **목적을 먼저 정하십시오.** 메모리를 줄이려는 것과 처리량을 올리려는 것은 **다른 스킴**으로 갑니다.
- `W4A16` 같은 표기는 **가중치(W) 4비트 / 활성값(A) 16비트**라는 뜻입니다. 이것만 읽을 줄 알면 절반은 끝납니다.
- **GGUF는 vLLM에서 "highly experimental and under-optimized"** 이고 **별도 플러그인**이 필요합니다. llama.cpp에서 쓰던 파일을 그대로 올리는 용도지, 성능을 기대할 자리가 아닙니다.
- **Hopper(H100) 이상이면 FP8(W8A8)** 이 기본값입니다 — 처리량 **+26.7%**, TPOT **−32.4%**, MMLU는 사실상 무손실.
- **Ampere(A100·A10) 이하면 W4A16** 이 메모리 절감용 기본값입니다. AWQ는 Turing 이상에서만 됩니다.
- **KV 캐시 양자화는 가중치 양자화와 별개의 레버**입니다. `--kv-cache-dtype fp8` 하나로 KV 메모리가 절반이 됩니다.
- 정확도는 생각보다 안 떨어집니다. Qwen3-8B 기준 MMLU가 BF16 74.78 → **FP8 74.79 / INT4-AWQ 73.59**.

## 1. 먼저 목적을 정하라 — 메모리인가 처리량인가

양자화 선택이 헷갈리는 이유는 **두 개의 다른 목적을 하나로 뭉쳐서** 보기 때문입니다.

| 목적 | 무엇이 문제인가 | 가는 방향 |
| --- | --- | --- |
| **메모리 절감** | 모델이 GPU에 안 올라감 / KV 캐시 자리가 없음 | 가중치 비트를 줄임 (4비트) |
| **처리량 향상** | 올라가긴 하는데 느림 | 활성값까지 줄여 **연산 자체를 저정밀도로** |

**가중치만 줄이면(W4A16) 메모리는 줄지만 연산은 여전히 16비트**입니다. 디코딩 단계처럼 메모리 대역폭이 병목인 구간에서는 이득이 있지만, 배치가 커져 연산이 병목이 되면 오히려 역전 구간이 생깁니다. 4비트 가중치를 매번 16비트로 풀어서(dequantize) 곱해야 하니까요.

**활성값까지 줄이면(W8A8) 텐서 코어가 저정밀도로 직접 곱합니다.** 여기서 진짜 처리량 이득이 나옵니다. 대신 그 정밀도를 지원하는 하드웨어가 있어야 합니다.

> 💡 **"모델이 안 올라간다"와 "느리다"는 다른 병목입니다.** 전자는 4비트, 후자는 FP8입니다. 이 구분을 안 하면 A100에 FP8을 올리려다 실패하거나, H100에서 W4A16을 쓰고 "왜 안 빨라지지" 하게 됩니다.

## 2. 표기법 읽기 — `W4A16`이 무슨 뜻인가

```
W4A16   →  Weight 4bit  /  Activation 16bit
W8A8    →  Weight 8bit  /  Activation 8bit
W4AFP8  →  Weight 4bit  /  Activation FP8   (혼합)
```

- **W(Weight)** — 모델 파라미터. 디스크·VRAM 점유를 결정합니다
- **A(Activation)** — 계산 중간값. 연산 정밀도를 결정합니다

그리고 같은 `W4A16`이라도 **어떤 알고리즘으로 4비트를 만들었느냐**가 또 갈립니다.

| 알고리즘 | 방식 | 특징 |
| --- | --- | --- |
| **RTN** | 그냥 반올림 | 가장 빠르고 간단. 보정 데이터 불필요 |
| **GPTQ** | 2차 근사로 오차 보정 | 보정 데이터 필요. 정확도 좋음 |
| **AWQ** | 중요한 채널을 보호 | 보정 데이터 필요. 4비트에서 강함 |

> 💡 **AWQ·GPTQ는 "포맷"이 아니라 "4비트를 만드는 방법"입니다.** 둘 다 결과물은 W4A16입니다. 그래서 "AWQ vs W4A16"이라는 비교는 성립하지 않습니다. 올바른 비교는 **AWQ vs GPTQ**(같은 층위)이거나 **W4A16 vs W8A8**(다른 층위)입니다.

## 3. GGUF — vLLM에서는 1순위가 아닙니다

GGUF는 llama.cpp 생태계의 포맷입니다. Ollama·LM Studio를 쓰다 온 사람에게는 가장 익숙하죠. 그런데 vLLM 공식 문서는 이렇게 적고 있습니다.

> **"GGUF support in vLLM is highly experimental and under-optimized at the moment"**

구체적으로 문서가 경고하는 것은 세 가지입니다.

- **다른 기능과 호환되지 않을 수 있습니다**
- **현재로서는 메모리 용량 축소 용도로만** 쓸 수 있습니다
- 문제가 나면 vLLM 팀에 보고하라고 안내합니다

게다가 GGUF 지원은 **out-of-tree 플러그인으로 분리**됐습니다. `vllm-gguf-plugin`을 따로 설치해야 서빙이 됩니다.

```bash
# 플러그인 설치가 선행돼야 합니다
pip install vllm-gguf-plugin

# 토크나이저는 베이스 모델에서 가져오는 것이 권장됩니다
vllm serve unsloth/Qwen3-0.6B-GGUF:Q4_K_M \
  --tokenizer Qwen/Qwen3-0.6B
```

`--tokenizer`를 따로 주는 이유는 문서가 명시합니다 — **GGUF 내장 토크나이저 변환이 오래 걸리고 버그가 있기 때문**입니다. 이걸 빼먹으면 서버가 뜨는 데 몇 분씩 걸리거나 토큰화가 이상해집니다.

> ⚠️ **GGUF를 vLLM에 올리는 것이 "틀린" 것은 아닙니다.** 이미 받아둔 GGUF가 있고 그것만 쓸 수 있는 상황이면 정당한 선택입니다. 다만 **성능을 기대하고 고르는 자리는 아닙니다.** 처리량이 목적이라면 같은 모델의 AWQ·GPTQ·FP8 체크포인트를 찾는 편이 훨씬 낫습니다.

## 4. AWQ와 GPTQ — 가중치만 줄이는 4비트

둘 다 4비트 가중치(W4A16)를 만드는 방법이고, vLLM에서 가장 널리 쓰입니다. 실질적인 차이는 **하드웨어 호환 범위**입니다.

| 방식 | Volta | Turing | Ampere | Ada | Hopper |
| --- | --- | --- | --- | --- | --- |
| **GPTQ** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **AWQ** | ❌ | ✅ | ✅ | ✅ | ✅ |
| **GGUF** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **bitsandbytes** | ✅ | ✅ | ✅ | ✅ | ✅ |
| **FP8 (W8A8)** | ❌ | ❌ | ❌ | ✅ | ✅ |

**GPTQ가 가장 넓게 돕니다.** V100 같은 Volta 세대까지 커버합니다. AWQ는 Turing 이상이지만 4비트 정확도에서 대체로 강합니다.

```bash
# 이미 양자화된 체크포인트를 그대로 서빙 — 대부분 이걸로 충분합니다
vllm serve Qwen/Qwen3-8B-AWQ

# 직접 만들 때는 llm-compressor를 씁니다
```

```python
from llmcompressor import oneshot
from llmcompressor.modifiers.quantization import GPTQModifier

recipe = GPTQModifier(targets="Linear", scheme="W4A16", ignore=["lm_head"])
oneshot(model=MODEL_ID, dataset="open_platypus",
        recipe=recipe, max_seq_length=2048, num_calibration_samples=512)
```

> 💡 **`lm_head`는 거의 항상 제외합니다.** 출력 레이어를 4비트로 누르면 생성 품질이 눈에 띄게 나빠집니다. 대부분의 레시피가 기본으로 빼둡니다.

## 5. W8A8 FP8 — 최신 GPU의 기본값

Ada(L40S·RTX 4090) 이상에는 FP8 텐서 코어가 있습니다. 여기서는 **가중치와 활성값을 모두 8비트로 두고 연산 자체를 FP8로** 돌립니다.

```bash
vllm serve neuralmagic/Meta-Llama-3.1-8B-Instruct-FP8
```

FP8에는 **정적(static)** 과 **동적(dynamic)** 이 있습니다.

- **정적** — 활성값 스케일을 보정 단계에서 미리 정해둠. **더 빠름**
- **동적** — 실행 중에 스케일을 계산. 보정이 필요 없어 **간편함**

실측(H100 기준)으로 정적이 동적보다 확실히 앞섭니다. 뒤 7장의 수치를 보십시오.

> ⚠️ **Ampere(A100·A10·RTX 3090)에는 FP8 텐서 코어가 없습니다.** FP8 체크포인트를 올려도 가속이 안 되거나 아예 안 뜹니다. A100에서 처리량을 올리고 싶다면 **W8A8-INT8**이 대안입니다.

## 6. GPU 세대별 선택표

llm-compressor 공식 문서가 제시하는 권장은 이렇습니다.

| GPU 세대 | Compute Capability | 1순위 | 대안 |
| --- | --- | --- | --- |
| **Blackwell** (B200) | 10.0 | **NVFP4 / MXFP4** (최대 압축) | MXFP8, FP8 |
| **Hopper** (H100·H200) | 9.0 | **W8A8-FP8** (최대 처리량) | W4AFP8 |
| **Ampere** (A100·A10·3090) | 8.0 | **W4A16** (메모리 절감) | W8A8-INT8 |
| **Turing** (T4·2080) | 7.5 | **W8A8-INT8** | W4A16 |

읽는 법은 단순합니다.

- **신형일수록 활성값까지 줄이는 쪽**으로 갑니다 (연산 이득)
- **구형일수록 가중치만 줄이는 쪽**으로 갑니다 (메모리 이득)

> 💡 **T4(16GB)에서 W8A8-INT8이 1순위인 게 의외일 수 있습니다.** T4에는 INT8 텐서 코어가 있어서 실제로 연산이 빨라지기 때문입니다. 반면 4비트는 T4에서 dequantize 비용이 이득을 갉아먹습니다.

## 6-1. 숫자로 먼저 계산하십시오 — VRAM 견적

스킴을 고르기 전에 **애초에 들어가는지**를 계산해야 합니다. 계산은 간단합니다.

```
가중치 VRAM ≈ 파라미터 수 × 비트/8

8B 모델 기준
  BF16 (16bit) →  8 × 2      = 16.0 GB
  FP8  ( 8bit) →  8 × 1      =  8.0 GB
  INT4 ( 4bit) →  8 × 0.5    =  4.0 GB
```

여기에 **오버헤드가 더 붙습니다.** 4비트라도 스케일·제로포인트 같은 메타데이터가 그룹 단위로 저장되므로 실제로는 계산값보다 10~20% 큽니다. 8B INT4는 4GB가 아니라 **4.5~5GB** 정도로 잡으십시오.

그리고 **남는 자리가 전부 KV 캐시가 됩니다.**

| GPU | BF16 8B | INT4 8B | INT4일 때 KV 여유 |
| --- | --- | --- | --- |
| RTX 4090 (24GB) | 16GB → 여유 ~6GB | 5GB → 여유 **~17GB** | 약 3배 |
| A100 (40GB) | 16GB → 여유 ~22GB | 5GB → 여유 **~33GB** | 약 1.5배 |
| H100 (80GB) | 16GB → 여유 ~62GB | 5GB → 여유 ~73GB | 약 1.2배 |

> 💡 **이 표가 "왜 4090에서 AWQ 이득이 46%나 되고 H100에서는 미미한가"를 설명합니다.** 여유 메모리가 3배로 뛰면 동시 처리 가능한 요청 수가 함께 뜁니다. 이미 여유가 큰 장비에서는 그 지렛대가 안 걸립니다.

70B급으로 가면 계산이 더 결정적입니다. BF16이면 140GB라 H100 한 장에 안 들어가지만, **INT4면 약 40GB로 A100 한 장에도 올라갑니다.** 이 구간에서는 양자화가 "선택"이 아니라 "가능/불가능"을 가릅니다.

## 6-2. 체크포인트 고르기 — 직접 만들 필요는 거의 없습니다

대부분의 경우 **이미 누가 만들어둔 것**을 쓰면 됩니다. Hugging Face에서 모델명 뒤에 붙는 접미사로 찾습니다.

```
Qwen/Qwen3-8B-AWQ                          ← AWQ 4비트
RedHatAI/Meta-Llama-3.1-8B-Instruct-FP8    ← FP8 W8A8
neuralmagic/…-quantized.w4a16              ← W4A16
unsloth/Qwen3-0.6B-GGUF                    ← GGUF (llama.cpp 계열)
```

고를 때 확인할 것은 세 가지입니다.

- **배포자가 누구인가** — `neuralmagic`·`RedHatAI`는 llm-compressor를 만든 팀이라 vLLM 호환성이 가장 확실합니다
- **모델 카드에 정확도 수치가 있는가** — 원본 대비 MMLU·GSM8K 회복률을 적어둔 체크포인트가 신뢰할 만합니다
- **`config.json`의 `quantization_config`** — 어떤 스킴인지 여기 적혀 있습니다. 접미사만 믿지 마십시오

직접 만들어야 하는 경우는 **사내 파인튜닝 모델**처럼 기성 체크포인트가 없을 때입니다. 그때 보정 데이터는 **실제 서비스 트래픽과 비슷한 것**을 쓰십시오. 범용 데이터셋으로 보정한 모델이 도메인 특화 입력에서 더 많이 깎이는 것은 자주 관측됩니다.

> ⚠️ **양자화된 모델을 다시 양자화하지 마십시오.** 이미 4비트인 체크포인트에 다시 레시피를 돌리면 오차가 누적됩니다. 항상 **원본 BF16/FP16에서 시작**하십시오.

## 7. 실측 — 얼마나 빨라지고 얼마나 나빠지나

### 처리량·지연 (ShareGPT 1,000 프롬프트 벤치마크)

**H100 80GB**

| 스킴 | 처리량 | TTFT | TPOT |
| --- | --- | --- | --- |
| **FP8 정적** | **+26.7%** | **−20.4%** | **−32.4%** |
| FP8 동적 | +14.8% | −14.1% | −21.8% |
| INT4-W4A16 | 기준선 대비 소폭 상승 | — | — |

**RTX 4090 24GB** — 메모리가 빠듯한 쪽에서 이득이 훨씬 큽니다.

| 스킴 | 처리량 |
| --- | --- |
| **AWQ** | **+46.1%** |
| GPTQ INT8 | +27.1% |

### 정확도 (Qwen3-8B, MMLU)

| 스킴 | MMLU | 차이 |
| --- | --- | --- |
| BF16 (기준) | 74.78 | — |
| **FP8 정적** | **74.79** | **사실상 무손실** |
| INT4-AWQ | 73.59 | −1.19 |

**이 표가 말하는 것은 두 가지입니다.**

① **FP8은 공짜에 가깝습니다.** 처리량이 27% 오르는데 MMLU는 그대로입니다. Hopper 이상이면 안 쓸 이유를 찾기가 어렵습니다.

② **4비트의 정확도 손실은 생각보다 작습니다.** MMLU 1.2점이면 대부분의 실무 용도에서 감내할 만합니다. **다만 "평균 점수"라는 점은 기억하십시오** — 코드 생성이나 수치 계산처럼 정밀도에 민감한 작업은 벤치 평균보다 더 나빠질 수 있습니다.

> ⚠️ **RTX 4090의 AWQ +46.1%를 "AWQ가 원래 그렇게 빠르다"로 읽으면 안 됩니다.** 24GB에 모델이 겨우 들어가던 상황에서 **KV 캐시 자리가 생겨 동시 처리량이 늘어난 것**입니다. 메모리에 여유가 있는 H100에서는 같은 이득이 나오지 않습니다. **양자화 이득의 상당 부분은 "배치를 더 키울 수 있게 된 것"에서 옵니다.**

## 8. KV 캐시 양자화 — 별도의 레버

가중치를 아무리 줄여도 **긴 컨텍스트에서 진짜 메모리를 먹는 것은 KV 캐시**입니다. 이건 별도로 켜야 합니다.

```bash
# 모든 레이어에 FP8
vllm serve meta-llama/Llama-3.1-8B --kv-cache-dtype fp8

# 하이브리드 어텐션 모델은 슬라이딩 윈도우 레이어를 빼는 편이 낫습니다
vllm serve gpt-oss-20b \
  --kv-cache-dtype fp8 \
  --kv-cache-dtype-skip-layers sliding_window
```

효과와 대가는 이렇습니다.

| 항목 | 값 |
| --- | --- |
| 메모리 | BF16 대비 **약 50% 절감** (토큰당 54% 수준) |
| 정확도 (추론 과제) | **1~2% 이내** 감소 |
| 정확도 (128k 롱컨텍스트) | AUC 기준 **97~98% 회복** |
| 지원 | Hopper=Flash Attention 3 · Blackwell=FlashInfer |

**주의할 조건이 명확합니다.**

- **7k 토큰 이하 컨텍스트에서는 BF16이 더 빠를 수 있습니다.** 짧은 요청만 처리하는 서비스라면 켜지 마십시오
- **`head_dim = 256`인 모델은 프리필이 약 1.6배 느려집니다**
- 하이브리드 어텐션 모델의 작은 윈도우 레이어는 BF16으로 두는 편이 낫습니다

> 💡 **긴 컨텍스트 서비스라면 가중치 양자화보다 KV 캐시 양자화가 먼저일 수 있습니다.** 128k 컨텍스트에서는 KV 캐시가 모델 가중치보다 큰 경우도 흔합니다.

### 언제 W4A16이 오히려 손해가 되는가

1장에서 "배치가 커지면 역전될 수 있다"고 했는데, 기준을 조금 더 구체적으로 잡아보겠습니다.

```
디코딩 단계  →  메모리 대역폭 병목  →  가중치를 적게 읽는 4비트가 유리
프리필 단계  →  연산 병목          →  16비트로 풀어 곱하는 4비트가 불리
```

즉 **입력이 길고 출력이 짧은 워크로드**(요약·분류·RAG 응답)는 프리필 비중이 커서 W4A16의 이득이 작습니다. 반대로 **짧게 넣고 길게 뽑는 워크로드**(생성·에이전트 루프)는 디코딩 비중이 커서 이득이 큽니다.

| 워크로드 | 프리필 : 디코딩 | W4A16 |
| --- | --- | --- |
| RAG 응답 (긴 컨텍스트, 짧은 답) | 높음 : 낮음 | 이득 작음 |
| 챗봇 대화 | 중간 : 중간 | 보통 |
| 코드 생성·에이전트 | 낮음 : 높음 | **이득 큼** |

> 💡 **내 트래픽의 입력·출력 토큰 비율을 먼저 재보십시오.** vLLM 로그의 `avg prompt throughput` 과 `avg generation throughput` 을 비교하면 대략 감이 잡힙니다. 이 비율을 모르고 스킴을 고르는 것은 찍는 것과 같습니다.

## 9. 흔한 오해 다섯 가지

| 오해 | 실제 |
| --- | --- |
| "양자화하면 무조건 빨라진다" | **W4A16은 배치가 커지면 느려질 수 있습니다.** dequantize 비용 때문 |
| "AWQ vs W4A16 중 뭐가 낫나" | **층위가 다릅니다.** AWQ는 W4A16을 만드는 방법 중 하나 |
| "GGUF가 vLLM에서도 표준" | **실험적이고 별도 플러그인**입니다. llama.cpp 생태계의 표준이지 vLLM의 표준이 아님 |
| "4비트는 품질이 많이 나빠진다" | MMLU 기준 **1.2점** 수준. 다만 코드·수치 작업은 별도 검증 필요 |
| "FP8이 최신이니 어디서나 최고" | **Ada 이상에만 텐서 코어가 있습니다.** A100에서는 이득이 없습니다 |

## 10. 실전 결정 순서

```
① GPU 세대 확인          → nvidia-smi --query-gpu=name,compute_cap --format=csv
② 목적 확정              → 안 올라감(메모리) / 느림(처리량)
③ 스킴 선택              → 6장 표
④ 기성 체크포인트 탐색    → HF에서 "-AWQ" "-FP8" "-GPTQ" 접미사 검색
⑤ 없으면 llm-compressor로 직접 제작
⑥ 긴 컨텍스트면 --kv-cache-dtype fp8 추가 검토
⑦ 골든 셋으로 정확도 확인 → 벤치 평균 말고 내 태스크로
```

```bash
# ①에 해당하는 한 줄
nvidia-smi --query-gpu=name,compute_cap,memory.total --format=csv
```

**⑦을 건너뛰지 마십시오.** MMLU 1.2점 차이가 내 서비스에서 어떻게 나타나는지는 내 데이터로만 알 수 있습니다. 평가 셋을 만드는 방법은 별도로 정리해두었습니다.

## 마무리

정리하면 결정은 두 줄로 끝납니다.

**Hopper 이상이면 FP8 정적을 기본으로 두십시오.** 처리량 +27%에 정확도 손실이 사실상 없습니다. **Ampere 이하면 W4A16(AWQ 또는 GPTQ)으로 메모리를 확보하고, 그렇게 생긴 자리를 KV 캐시에 쓰십시오.** 24GB급에서 처리량이 46% 뛴 것도 결국 그 효과였습니다.

**GGUF는 이미 가진 파일을 급히 올려야 할 때의 선택지**로 남겨두는 편이 낫습니다. vLLM이 스스로 실험적이라고 표시해둔 경로에 프로덕션을 얹을 이유는 없습니다.
